# ogentic-audit — On-disk format spec, v0.2 (signed mode)

**Status:** Draft (depends on [ADR-0004](../adr/0004-signed-chain-and-offline-verification.md)). Normative once ADR-0004 is Accepted and the v0.2 golden vectors are committed.
**Last updated:** 2026-10-03
**Format version:** `0x0002`. Format `0x0001` ([v0.1](v0.1.md), HMAC-SHA256) is unchanged and remains a valid, supported mode.

v0.2 adds a **signed** format in which the party that writes the log and the party that verifies it can be different principals. Every record carries an Ed25519 signature; records are linked by a public SHA-256 hash; verification needs only the signer's **public** key. Nobody who verifies a v0.2 log can forge one.

This document specifies, byte for byte:

1. the signed log format (segment header, record framing, record schema, chain);
2. **signed checkpoints** — portable, signed statements of a log's head;
3. **release attestations** — a signed index of every file in a release plus the audit-log head, verifiable offline;
4. **key statements** — rotation (transition) and revocation;
5. the **verification algorithm**, with every failure mode and the report kind it produces.

Everything not restated here is inherited from [v0.1](v0.1.md): canonical CBOR rules, timestamp rules, payload conventions, file naming, crash-recovery framing.

## 1. Goals and non-goals

**Goal.** A third party (a requester, an auditor, a court) holding a log or a release, and a public key obtained **outside** that log or release, can establish without any secret and without the writing application installed:

- every record was produced by the holder of the matching private key;
- no record was altered, removed, reordered, or inserted, up to a pinned head;
- every attested file in a release is byte-identical to what the signer released, and the audit-log head is the one the signer released with it.

**Non-goals.** Confidentiality (records are plaintext; see v0.1). Trusted time (`ts_wall` and `created_at` are the signer's clock; see §14). Multiple concurrent writers on one log. Detecting a signer who rewrites their own log **without** an independently held checkpoint (§10.4 — the defense is checkpoints, not the format).

## 2. Terminology (additions to v0.1)

| Term | Definition |
|------|------------|
| **Signer** | The holder of an Ed25519 private key that signs a log, checkpoint, attestation, or statement |
| **Public key** | The 32-byte Ed25519 public key ([RFC 8032 §5.1.5](https://www.rfc-editor.org/rfc/rfc8032#section-5.1.5)) |

| **Trust context** | The verifier's pins, plus key statements and revocations (§9) |

| `‖` | Byte concatenation |

## 3. Cryptography

### 3.1 Primitives

A conforming v0.2 verifier needs exactly: **Ed25519** (with SHA-512, as RFC 8032 defines), **SHA-256**, **CRC32** (corruption detection only, never security), canonical **CBOR** (v0.1 rules), canonical **JSON** (§3.6), and **base64** (RFC 4648 §4). It does **not** need HMAC, BLAKE3, or any secret. Every one of these is available in the standard library or one common package of every mainstream language; Ed25519 + SHA-256 are what OpenSSH, Go `crypto/ed25519`, Node `crypto`, OpenSSL ≥ 1.1.1, and Python `cryptography` provide.

### 3.2 Algorithm identifiers

| `sig_alg` (u16) | JSON `alg` | SSH key type | Public key | Signature | Status |
|---|---|---|---|---|---|
| `0x0000` | — | — | — | — | invalid |
| `0x0001` | `"ed25519"` | `ssh-ed25519` | 32 B | 64 B | **defined** |
| `0x0002` | `"ml-dsa-65"` | reserved | 1952 B | 3309 B | **reserved** (FIPS 204; §15) |
| others | — | — | — | — | unassigned |

The algorithm identifier is bound into every signed byte string: into each record (key 12), into the segment header (hashed into the chain start), into the key blob (and therefore `key_id`), and into every SSHSIG (key type and signature type strings). A verifier MUST check all of them agree; it never infers the algorithm from a length.

### 3.3 Signatures: SSHSIG with a namespace

Every signature in v0.2 — per record, per checkpoint, per attestation, per key statement — is an Ed25519 signature over the **SSHSIG signed data** defined by OpenSSH [`PROTOCOL.sshsig`](https://github.com/openssh/openssh-portable/blob/master/PROTOCOL.sshsig):

```
signed_data(namespace, message) =
    "SSHSIG"                      (6 ASCII bytes, no length prefix)
  ‖ string(namespace)
  ‖ string("")                    (reserved, empty)
  ‖ string("sha512")
  ‖ string(SHA-512(message))
signature = Ed25519-Sign(private_key, signed_data(namespace, message))
```

We invent no signature construction: SSHSIG is a published, deployed domain-separation scheme, and it makes every detached signature in this spec checkable with `ssh-keygen -Y verify` (OpenSSH ≥ 8.1), which ships with macOS and most Linux distributions and is available for Windows.

| Namespace | Signs | Message |
|-----------|-------|---------|
| `ogentic-audit/v0.2/record` | a log record | the record's `payload_bytes` |
| `ogentic-audit/v0.2/checkpoint` | a signed checkpoint (§10) | the checkpoint file bytes |
| `ogentic-audit/v0.2/release` | a release attestation (§11) | the attestation file bytes |
| `ogentic-audit/v0.2/key-transition` | a key transition statement (§9.3) | the statement file bytes |
| `ogentic-audit/v0.2/key-revocation` | a revocation statement (§9.4) | the statement file bytes |

A signature valid in one namespace is invalid in every other, so no signed object can be replayed as another kind.

**On disk, inside a log**, only the raw 64-byte signature is stored (the key and namespace are implied). **Detached signatures** (checkpoints, attestations, statements) are stored as the full armored SSHSIG blob in a sibling file named `<file>.sig`:

```
blob =
    "SSHSIG"
  ‖ uint32(1)                                   (SIG_VERSION)
  ‖ string(key blob)
  ‖ string(namespace)
  ‖ string("")
  ‖ string("sha512")
  ‖ string( string("ssh-ed25519") ‖ string(signature) )

armored =
    "-----BEGIN SSH SIGNATURE-----\n"
  ‖ base64(blob), wrapped at 70 characters per line, each line ending "\n"
  ‖ "-----END SSH SIGNATURE-----\n"
```

Writers MUST emit exactly this armor (it is what `ssh-keygen -Y sign` emits). Readers MUST accept any line length and ignore `\r`. A verifier parsing a detached signature MUST reject any blob whose magic is not `SSHSIG`, whose version is not 1, whose namespace differs from the one the object type requires, whose hash algorithm is not `sha512`, whose reserved field is non-empty, whose key type or signature type is not `ssh-ed25519`, or which has trailing bytes. For a release attestation that rejection is the violation `SignatureInvalid` (reason `malformed`, `namespace`, `hash_alg`, or `key_type`). For a checkpoint or a revocation passed in by the operator it is an error (§8.4). For a statement found in a bundle it is a warning (§9.2). (`ssh-keygen` also accepts `sha256`; v0.2 writers never produce it and v0.2 verifiers reject it, so there is one encoding per signature.)

### 3.4 Hashes with domain separation

```
TH(tag, data) = SHA-256( tag ‖ 0x00 ‖ data )
```

| Tag (ASCII, no NUL) | Input | Output |
|---------------------|-------|--------|
| `ogentic-audit/v0.2/header` | segment header bytes, CRC excluded | `chain_start` |
| `ogentic-audit/v0.2/record` | record `payload_bytes` | `record_hash` |

`key_id` is the one untagged hash: `SHA-256(key blob)`, so that it equals the OpenSSH fingerprint. A key blob begins `00 00 00 0b`, which no tagged input can.

### 3.5 Strict verification

Ed25519 verification MUST be the strict rule set (cofactorless, as implemented by `ed25519-dalek` 2.x `verify_strict`):

1. `S` MUST be canonical (`S < L`).
2. The public key `A` MUST NOT be a point of small order (order dividing 8).
3. The signature point `R` MUST NOT be a point of small order.
4. `A` and `R` MUST decode as valid curve points; the cofactorless equation `[S]B = R + [k]A` MUST hold.

A failure of any rule is `SignatureInvalid` (reason `noncanonical` for rule 1, `weak_key` for 2, `mismatch` otherwise). A public key failing rule 2 MUST also be refused when **pinned** (argument error), because anyone can produce signatures that verify under a small-order key.

`ssh-keygen` is less strict about `S`: OpenSSH 10.3 accepted a signature with `S` replaced by `S + L`, which OpenSSL rejects. That divergence only admits an alternative encoding of a signature the key holder already made over the same message; it never admits a signature on a new message. The stock-tools path (§11.7) is therefore sound, and the `ogentic-audit` verifiers are the stricter of the two.

### 3.6 Canonical JSON

Checkpoints, attestations, and key statements are JSON documents in **canonical form**: [RFC 8785 (JCS)](https://www.rfc-editor.org/rfc/rfc8785) restricted to this subset, under which JCS is trivial to reproduce:

- values are objects, arrays, strings, or integers in `[0, 2^53 − 1]` — no floats, negatives, booleans, or `null`;
- object keys are ASCII; keys are sorted by byte order; no duplicate keys;
- optional members are **omitted**, never `null`;
- no whitespace outside strings; strings are UTF-8, escaping only `"`, `\`, and U+0000–U+001F (as `\b \f \n \r \t` or `\u00xx` with lowercase hex);
- the file is exactly the canonical bytes — no BOM, no trailing newline.

Python's `json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)` produces this form for the subset. A verifier MUST parse the file, re-serialize it canonically, and reject (`AttestationMalformed`, or the argument error for a pin/statement file) if the bytes differ. This closes parser differentials (duplicate keys, alternative escapes) between our verifier, `jq`, and any third party's parser: there is one byte string per document.

### 3.7 Public key formats and fingerprints

**Export formats** (all equivalent; a verifier accepts each wherever a public key is expected):

| Format | Example (RFC 8032 §7.1 TEST 1 key) |
|--------|---------|
| OpenSSH line (default) | `ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAINdamAGCsQq31Uv+08lkBzoO4XLz2qYjJa8CGmj3B1Ea <comment>` |
| PEM SubjectPublicKeyInfo ([RFC 8410](https://www.rfc-editor.org/rfc/rfc8410)) | `-----BEGIN PUBLIC KEY-----` / `MCowBQYDK2VwAyEA11qYAYKxCrfVS/7TyWQHOg7hcvPapiMlrwIaaPcHURo=` / `-----END PUBLIC KEY-----` |
| Raw hex | `d75a980182b10ab7d54bfed3c964073a0ee172f3daa62325af021a68f707511a` |

**Fingerprint text forms** of the same 32 `key_id` bytes:

| Form | Use | Example |
|------|-----|---------|
| Grouped hex | Reading aloud, printing on letters and web pages | `6db5 e9b8 a1ba ce1c dd9a 7c6a db9e 9396 acc5 0734 65d9 fe8e 3a0e f6d9 c60d 6d4f` |
| OpenSSH | Cross-checking with `ssh-keygen -l -f key.pub` | `SHA256:bbXpuKG6zhzdmnxq256TlqzFBzRl2f6OOg722cYNbU8` |

Grouped hex is the primary human form: 16 groups of 4 characters from a 16-symbol, case-insensitive alphabet, unambiguous over a phone line. The full 256 bits are always shown; there is no short form, so nobody pins a truncation. Parsers accept hex with any mix of spaces, `-`, or `:` separators and either case, or the `SHA256:` form. The example values above were cross-checked with OpenSSH 10.3 (`ssh-keygen -l`).

## 4. Segment header

Segment files keep v0.1 naming (`audit-NNNN.cbor`). The header length depends on `sig_alg`: `H = 80 + P`, where `P` is the public-key length (Ed25519: `P = 32`, `H = 112`).

| Offset | Length | Field | Notes |
|--------|--------|-------|-------|
| 0 | 4 | `magic` | ASCII `"OGAU"` |
| 4 | 2 | `version` | u16 LE, `0x0002` |
| 6 | 2 | `segment_index` | u16 LE; MUST equal the index in the file name |
| 8 | 2 | `sig_alg` | u16 LE (§3.2) |
| 10 | 2 | `reserved` | zero |
| 12 | 32 | `key_id` | `SHA-256(key blob)` of `public_key` |
| 44 | 32 | `prev_final` | segment 0: 32 zero bytes; segment N ≥ 1: `record_hash` of the last record of segment N−1 |
| 76 | `P` | `public_key` | the signer's public key — **informational until pinned** (§9) |
| 76+`P` | 4 | `header_crc` | u32 LE, CRC32 (IEEE 802.3) of bytes `[0, 76+P)` |

```
chain_start_N = TH("ogentic-audit/v0.2/header", header_N[0 .. 76+P))
```

Every segment's header — not only segment 0's — is hashed into its `chain_start`, which record 0 of that segment signs (as `prev_hash`). The whole header (index, algorithm, key, continuity link) is therefore covered by a signature as soon as the segment has a record.

A v0.1 reader checks `version` before the CRC and reports `UnknownVersion` for any v0.2 segment; it never misreads one.

**Example** — genesis header for the RFC 8032 TEST 1 key (112 bytes):

```
0000  4f 47 41 55 02 00 00 00 01 00 00 00 6d b5 e9 b8
0010  a1 ba ce 1c dd 9a 7c 6a db 9e 93 96 ac c5 07 34
0020  65 d9 fe 8e 3a 0e f6 d9 c6 0d 6d 4f 00 00 00 00
0030  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
0040  00 00 00 00 00 00 00 00 00 00 00 00 d7 5a 98 01
0050  82 b1 0a b7 d5 4b fe d3 c9 64 07 3a 0e e1 72 f3
0060  da a6 23 25 af 02 1a 68 f7 07 51 1a 7e 2e 29 3d
chain_start_0 = cdd6a6884fe9f169eac8159c537bfe5dc61d9ec387d8cd3001d014f3afabeb99
```

**One key per log.** Every segment of a log MUST carry the same `sig_alg`, `key_id`, and `public_key` as segment 0. Rotation starts a new log (§9.3); it never changes the key inside one. (See ADR-0004 D8 for why.)

## 5. Record framing

| Length | Field | Notes |
|--------|-------|-------|
| 4 | `len_prefix` | u32 LE, length of `payload` |
| `len_prefix` | `payload` | canonical CBOR record map (§6) |
| `S` | `signature` | raw signature; `S` from §3.2 (Ed25519: 64) |
| 4 | `len_trailer` | u32 LE, MUST equal `len_prefix` |

```
signature_n = Ed25519-Sign(sk, signed_data("ogentic-audit/v0.2/record", payload_bytes_n))
record_hash_n = TH("ogentic-audit/v0.2/record", payload_bytes_n)
```

`record_hash` covers the payload, not the signature. Record identity is therefore independent of signature encoding (with strict verification there is only one accepted encoding anyway), and a checkpoint pins content, not a signature byte string.

## 6. Record schema

A CBOR map with integer keys, canonical per v0.1 §"Canonical encoding rules".

| Key | Field | Type | v0.2 rule |
|-----|-------|------|-----------|
| 1 | `record_id` | uint | MUST equal the record's position in its segment (0, 1, 2, …) |
| 2 | `prev_hash` | bstr 32 | record 0 of segment N: `chain_start_N`; otherwise the preceding record's `record_hash` |
| 3 | `ts_wall` | tstr | as v0.1 |
| 4 | `ts_mono_delta` | uint | as v0.1 |
| 5 | `session_id` | bstr 16 | as v0.1 |
| 6 | `actor` | tstr | as v0.1 |
| 7 | `event` | tstr | as v0.1 |
| 8 | `payload` | map | as v0.1 (text keys) |
| 9 | `key_id` | bstr 32 | MUST equal header `key_id` |
| 10 | `schema_version` | uint (u8) | as v0.1 |
| 11 | `segment_index` | uint (u16) | MUST equal header `segment_index` |
| 12 | `sig_alg` | uint (u16) | MUST equal header `sig_alg` |

All twelve keys are required. Keys 13–99 MUST be rejected. Keys ≥ 100 stay reserved for additive optional fields, as in v0.1. Each record thus names its own position, log key, and algorithm inside the signed bytes, so a record extracted on its own (into an exhibit or a checkpoint) still says where it came from and how to check it.

**Payload conventions** carry over from v0.1, with one change: `segment.finalized`'s `final_hash` is the preceding record's `record_hash`. The `policy` convention (ADR-0003) is unchanged. One optional convention is added:

- **`log.continued`** — the first record of a log MAY carry `payload["previous_log"]` = `{ "log_id": bstr 32, "segment": uint, "record_id": uint, "record_hash": bstr 32, "key_id": bstr 32 }`, naming the final head of the log it follows (for example after a key rotation). Verifiers treat it as data. It links the two logs for a reader; it is not a trust path.

## 7. Chain invariants

For a log with segments `0..n`:

1. Segment 0's `prev_final` is 32 zero bytes. Segment N ≥ 1's `prev_final` equals the `record_hash` of segment N−1's last record. Only the **last** segment may hold no records (the writer creates a header before its first append). A record-less segment followed by another segment is `SegmentDiscontinuity` at the following segment.
2. Record 0 of every segment has `prev_hash = chain_start_N`. Every other record has `prev_hash` = the preceding record's `record_hash`.
3. Every record's signature verifies (strictly, §3.5) under the header public key in namespace `ogentic-audit/v0.2/record`.
4. Every record's `record_id`, `segment_index`, `key_id`, `sig_alg` agree with its position and header.
5. Timestamp rules are v0.1's.

Because each signature covers `prev_hash`, the signature on any record commits to the entire history before it. **The signature on the head record is a signed head**; a separate periodic signature would add nothing.

Rollover follows v0.1: a `segment.finalized` record, `fsync`, then the next segment's header.

### 7.1 Writer obligations

- Append-only, `F_FULLFSYNC`/`fsync` discipline, and torn-tail recovery as in v0.1. On reopen, the writer verifies the signature of every record it walks (it holds the public key) and refuses to resume past a complete record whose signature fails.
- A writer MUST refuse to append to a log whose format, algorithm, or key differs from its own (no mixed-format or mixed-key logs).
- A writer MUST NOT expose the private key through any API; signing happens behind a `Signer` handle (§13).

## 8. Verifying a log

### 8.1 Inputs and mode

Inputs: the log directory; a trust context (pins, statements, revocations — any may be empty); optionally a checkpoint (§10).

The verifier reads segment 0's `version`:

| Segment 0 version | Caller supplied | Result |
|---|---|---|
| `0x0002` | trust context (any pin) | signed verification (§8.2) |
| `0x0002` | nothing | signed verification; the best verdict is `SelfConsistent` |
| `0x0002` | an HMAC key (v0.1 mode) | **argument error** (exit 3): "this is a signed log; pass a public key or fingerprint". Never an HMAC verification |
| `0x0001` | trust context | violation **`FormatDowngrade@s0`** (exit 1). The caller expected a signed log and was handed an HMAC log, which anyone holding that HMAC key can forge |
| `0x0001` | an HMAC key, or nothing | v0.1 verification, unchanged (an HMAC key is required) |

No segment files: an error (`NoSegments`, exit 2), never a report.

### 8.2 Algorithm

```
segments = list audit-NNNN.cbor in index order
final = 0^32;  signed_ok = false;  count = 0
for (N, file) in segments:
    H = parse_header(file, expected_prev_final = final)   # H1–H12, in order
    if N == 0 and any pin was given and H.key_id is not trusted (§9.5):
        → UntrustedSigner@s0, stop
    prev = chain_start(H)
    for (p, rec) in records(file):                         # R1–R8, in order
        prev = record_hash(rec);  count += 1
        if the signature verified and H.key_id is trusted: signed_ok = true
    final = prev        # a record-less segment must be the last one (§7)

if a checkpoint was supplied: check it (§10.3)

verdict = Violation       if any violation
        = Verified        if signed_ok
        = SelfConsistent  otherwise   (no pin given, or no record was signed)
```

`Verified` requires **at least one signature verified under a key the verifier trusts**. A header-only log, or any log checked without a pin, can at best be `SelfConsistent`. The `log_id` is set from segment 0 record 0.

### 8.3 Checks, order, and report kinds

Checks run in this order; the first failure is the reported violation (forensic mode continues, as v0.1). Locations use the record's **position** (`s<segment>r<position>`), and the evidence carries any value the record claims.

**Segment header** (location `s<N>`):

| # | Check | Kind | Evidence |
|---|-------|------|----------|
| H1 | file ≥ 12 bytes | `HeaderCorrupt` (`Truncated`) | message |
| H2 | `magic == "OGAU"` | `HeaderCorrupt` (`BadMagic`) | actual magic |
| H3 | `version == 0x0002` | `FormatDowngrade` if `0x0001` (a v0.1 segment in a v0.2 log, or §8.1 row 4); else `UnknownVersion` | actual, expected version |
| H4 | `sig_alg` implemented | `UnsupportedAlgorithm` | actual `sig_alg`, supported list |
| H5 | file ≥ `H` bytes | `HeaderCorrupt` (`Truncated`) | message |
| H6 | CRC32 over `[0, 76+P)` | `HeaderCorrupt` (`CrcMismatch`) | expected, actual CRC |
| H7 | `reserved == 0` | `HeaderCorrupt` (`ReservedBytesNonZero`) | actual bytes |
| H8 | `public_key` passes §3.5 rule 2 | `SignatureInvalid` (`weak_key`) | key |
| H9 | `key_id == SHA-256(key blob(public_key))` | `KeyIdMismatch` | header `key_id`, computed |
| H10 | N ≥ 1: `sig_alg`, `key_id`, `public_key` equal segment 0's | `AlgorithmMismatch` / `KeyIdMismatch` | both values |
| H11 | `segment_index` equals the file-name index | `SegmentDiscontinuity` | expected, actual index |
| H12 | `prev_final` (zero for N = 0; else previous segment's final `record_hash`) | `HeaderCorrupt` (`GenesisPrevFinalNonZero`) for N = 0; `SegmentDiscontinuity` for N ≥ 1 | expected, actual |

**Record** (location `s<N>r<p>`):

| # | Check | Kind | Evidence |
|---|-------|------|----------|
| R1 | framing complete, `len_trailer == len_prefix` | `RecordCorrupt` (`TornTail`) | byte offset |
| R2 | signature verifies strictly over `signed_data(record ns, payload_bytes)` | `SignatureInvalid` (`mismatch` / `noncanonical`) | payload offset and length, signature hex, `key_id` |
| R3 | payload is canonical CBOR with the §6 schema | `RecordCorrupt` (`DecodeError`) | decoder message |
| R4 | `key_id` field == header | `KeyIdMismatch` | both |
| R5 | `sig_alg` field == header | `AlgorithmMismatch` | both |
| R6 | `segment_index` == N, `record_id` == p, `prev_hash` == expected | `ChainBreak` | expected/actual `prev_hash`, expected/actual position, `is_segment_start` |
| R7 | key not revoked at this position (§9.4) | `RevokedKey` | revocation `issued_at`, trusted head if any |
| R8 | timestamp rules (v0.1) | `TimestampRegression` / `TimestampInconsistency` | as v0.1 |

**Why signature before decode and before the chain (R2 first).** A flipped byte anywhere in a record's payload or signature makes R2 fail **at that record**, so the report names the altered item rather than a decode error or a chain break one record later. A record whose signature verifies but whose position or `prev_hash` is wrong is a genuine record in the wrong place: deleted neighbour, reordering, or a splice from another log by the same key. That is `ChainBreak`. The two kinds therefore separate "altered" from "moved or missing".

**What each attack reports.** One byte changed in a record → `SignatureInvalid@sNrP` naming it. Signature bytes changed → `SignatureInvalid@sNrP`. Record removed → `ChainBreak` at the removed record's position. Records swapped → `ChainBreak` at the first swapped position. Middle segment deleted → `SegmentDiscontinuity`. Log re-signed with another key → `UntrustedSigner@s0` (when pinned). v0.1 segment substituted → `FormatDowngrade@sN`. Tail truncated, or rewritten by the key holder → **not detectable without a checkpoint** (§10); with one, `CheckpointTruncated` / `CheckpointMismatch`.

### 8.4 Errors (not violations)

Operator mistakes never read as accusations; they are errors, as in v0.1: no segments (`NoSegments`, exit 2); unreadable directory (exit 2); a malformed pin, trust file, or out-of-band revocation file, or a pinned weak key (exit 3); an HMAC key for a v0.2 log (exit 3); a v1 (HMAC) checkpoint for a v0.2 log, or a v2 checkpoint for a v0.1 log (exit 3); a checkpoint whose `log_id` names a different log (`CheckpointForDifferentLog`, exit 3); a checkpoint signature that does not verify, or verifies under an untrusted key (exit 3); a `--revocations` file that does not verify, or is signed by neither a pinned key nor the key it revokes (exit 3). A revocation the verifier cannot honour must stop the run, never be skipped.

### 8.5 Verdicts and exit codes

| Verdict | Meaning | CLI exit | JSON `status` |
|---------|---------|----------|---------------|
| `Verified` | No violation, and at least one signature verified under a trusted key | 0 | `"ok"` |
| `SelfConsistent` | No violation, but the signer is not pinned or nothing was signed. **Not a verification.** The CLI prints `Self-consistent, signer not pinned` and the signer's grouped fingerprint | **4** | `"unpinned"` |
| `Violation` | At least one violation | 1 | `"tampered"` |

Exit code 4 is new and is produced only by v0.2 inputs; v0.1 behaviour and exit codes are unchanged. Scripts that treat any non-zero exit as failure fail closed on `SelfConsistent`.

## 9. Trust: pins, rotation, revocation

### 9.1 Pins

A pin is a public key or fingerprint the verifier obtained **outside** the artefact under verification: from the signer's website, a letter, a phone call, a prior release, a court filing. Sources, all accepted by the CLI and both libraries:

- `--public-key <file|line>`: a public key in any §3.7 format;
- `--key-fingerprint <fp>` (repeatable): a fingerprint in either §3.7 form. The public key bytes then come from the artefact (segment header, SSHSIG blob, or transition statement) and are accepted only if they hash to the pinned fingerprint;
- `--trust <file>`: a **trust file** — the OpenSSH `allowed_signers` format restricted to lines of the form `<principal> ssh-ed25519 <base64> [comment]` (no options; `#` comments and blank lines allowed). The same file therefore works for `ssh-keygen -Y verify -f`.

A public key embedded in a segment header, in an SSHSIG blob, in `ogentic-audit-signer.pub`, or printed in a release's instructions is **informational only**. It is never a pin. A verifier with no pin MUST NOT report `Verified` (§8.5).

### 9.2 Statements

Key transitions and revocations are canonical-JSON files with detached SSHSIG signatures (`<name>.json` + `<name>.json.sig`). They are self-authenticating, so they may travel inside an untrusted bundle (directory `ogentic-audit-keys/`) or be passed with `--statements <dir>`. A transition can only extend trust from a key the verifier already trusts. A revocation can only reduce trust. An unparseable or unverifiable statement found in a bundle is ignored with a warning; it never adds trust.

### 9.3 Key transition (rotation)

```json
{"format":"ogentic-audit-key-transition/v1","issued_at":"2027-01-15T09:00:00.000Z","new_key_id":"<64 hex>","new_public_key":"ssh-ed25519 AAAA…","old_key_id":"<64 hex>","reason":"scheduled"}
```

(Shown in canonical form: sorted keys, no whitespace. `reason` is optional free text.) It is signed by the **old** key in namespace `ogentic-audit/v0.2/key-transition`. `new_key_id` MUST equal `SHA-256(key blob(new_public_key))`. The new key does not co-sign. A transition only lets logs signed by the new key verify under a pin of the old one; the old key's holder could not use it to forge anything signed by the new key.

Rotation is: generate the new key; sign the transition with the old key; close the current log (signed checkpoint, §10); open **new** logs with the new key; ship the transition in `ogentic-audit-keys/` with every later release; keep or destroy the old private key ([key-rotation.md](../security/key-rotation.md#signed-mode-format-0x0002)). Logs never change key mid-stream (§4). A verifier pinned to the root key reaches any later key through the chain of transitions.

### 9.4 Revocation

```json
{"format":"ogentic-audit-key-revocation/v1","issued_at":"…","reason":"compromised","revoked_key_id":"<64 hex>","trusted_heads":[{"key_id":"…","log_id":"…","record_count":42,"record_hash":"…","record_id":41,"segment":0}],"trusted_successors":["<64 hex>"]}
```

Signed in namespace `ogentic-audit/v0.2/key-revocation` by a **pinned** key or by the **revoked key itself**. Self-revocation can only reduce trust, so it is always honoured. Revocations are for **compromise**. Ordinary retirement is a transition, and logs signed before it stay valid.

After a revocation of key K, a signature by K is accepted only:

- on a record of a log listed in `trusted_heads` (matched by `log_id`), at or before that head's position, with that head's `record_hash` present at that position (otherwise `CheckpointMismatch` against the head); and
- on a transition to a key listed in `trusted_successors`.

Everything else signed by K is `RevokedKey`: later records, other logs, checkpoints, release attestations. A revoked signer re-issues release attestations under its new key; the released files are unchanged.

**Distribution.** A verifier cannot learn of a revocation it is not given. Revocations MUST be published through the same out-of-band channel as the pins, and verifiers MUST pass them in (`--revocations <file>`, repeatable). A bundle may also carry them, but omitting one from a bundle is exactly what an attacker would do. (Residual risk, threat model.)

### 9.5 Trust evaluation

```
trusted_keys = pins
loop until no change:
    for each verified transition T (old → new):
        if T.old ∈ trusted_keys
           and (T.old is not revoked
                or T.new ∈ revocation(T.old).trusted_successors):
            trusted_keys += T.new   (trust_path(new) = trust_path(old) + [new])
```

A key is trusted iff it is in `trusted_keys`. The report records the `trust_path` (pinned key first). Revocations are evaluated per signature (§9.4 and check R7). Pinning the **newest** key you can obtain out of band is strongest: a compromised **intermediate** key can mint transitions that a root-only pin would follow until its revocation reaches you.

## 10. Signed checkpoints

### 10.1 Format

```json
{"alg":"ed25519","format":"ogentic-audit-checkpoint/v2","head_ts_wall":"2026-10-03T11:59:58.120Z","key_id":"<64 hex>","log_id":"<64 hex>","observed_at":"2026-10-03T12:00:00.000Z","record_count":42,"record_hash":"<64 hex>","record_id":41,"segment":0}
```

| Field | Meaning |
|-------|---------|
| `key_id` | the log's signer |
| `log_id` | `record_hash` of s0r0 — which log |
| `segment`, `record_id` | position of the head (`record_id` ≤ 2^53−1) |
| `record_count` | records from s0r0 through the head, inclusive, across segments (≥ 1: a log with no records has no head to checkpoint) |
| `record_hash` | the head's `record_hash` |
| `head_ts_wall` | the head record's `ts_wall` (copied; signed-clock time) |
| `observed_at` | when the checkpoint was made (signed-clock time) |

The file is canonical JSON (§3.6). It MAY have a detached signature `<file>.sig` in namespace `ogentic-audit/v0.2/checkpoint`:

- **signed by the log's signer**: the signer's own non-repudiable statement "my log had this head". Anyone holding it can later prove truncation or rewrite against the signer;
- **signed by a witness** (any other key): the witness attests it observed this head. External witnessing needs no other mechanism;
- **unsigned**: the verifier's own observation, worth what the verifier's own record-keeping is worth.

v1 checkpoints (`ogentic-audit-checkpoint/v1`, HMAC) remain the format for v0.1 logs. The formats are never interchangeable (§8.4).

### 10.2 Making one

`ogentic-audit checkpoint <log>` needs no key. Anyone holding a log can record an unsigned v2 observation after verifying it. With `--sign <signer>`, the writer's key signs it. The signer SHOULD hand signed checkpoints to parties with different interests (the requester, an auditor, a transparency log) at meaningful moments: release, session close, rotation.

### 10.3 Verifying against one

After the walk (§8.2):

1. A `.sig` is present → it MUST verify (namespace, strictness) under a trusted key → else **error** `CheckpointSignatureInvalid` / `CheckpointSignerUntrusted` (exit 3). A checkpoint that cannot be authenticated is not evidence about the log, so it never produces a violation against the log.
2. `log_id` ≠ this log's → error `CheckpointForDifferentLog` (exit 3), as v0.1's key mismatch.
3. The position does not exist → **`CheckpointTruncated`** (history the checkpoint saw is gone).
4. The position exists but its `record_hash`, or `record_count` at that position, differs → **`CheckpointMismatch`** (history rewritten).

### 10.4 Equivocation evidence

Two checkpoints signed by the same key with the same `log_id` and position but different `record_hash` are a self-contained, verifiable proof that the signer published two histories. This is the strongest answer to a signer who rewrites their own log, and it needs only that someone kept an earlier signed checkpoint.

## 11. Release attestation (the offline verifier bundle)

### 11.1 Bundle layout

```
<release>/
  …released files…                       (any depth)
  <log dir>/audit-NNNN.cbor              one or more v0.2 logs
  ogentic-audit-release.json             the attestation (canonical JSON)
  ogentic-audit-release.json.sig         SSHSIG, namespace ogentic-audit/v0.2/release
  ogentic-audit-signer.pub               OpenSSH line — informational, never a pin
  ogentic-audit-keys/                    optional: transition / revocation statements
  ogentic-audit-verifier/                optional: verifier binaries / wheels + provenance signatures
```

The five `ogentic-audit-*` names above are the **reserved bundle entries**.

The bundle MAY also include verifier binaries and wheels (in `ogentic-audit-verifier/`) together with their release-provenance signatures (sigstore `.sig` / `.pem`, as published for the CLI), so an offline machine can check the verifier's provenance against the public build pipeline rather than against the signer. A human-readable instructions file, if present, is an attested file, and MUST tell the reader to obtain the signer's fingerprint from an independent source; it MUST NOT present a fingerprint printed inside the bundle as the one to pin.

### 11.2 Format

```json
{
  "alg": "ed25519",
  "created_at": "2026-10-03T12:00:00.000Z",
  "files": [
    {"parts": [{"length": 14, "name": "header", "offset": 0, "sha256": "<64 hex>"},
               {"length": 4, "name": "row 1", "offset": 14, "sha256": "<64 hex>"}],
     "path": "Index.csv", "role": "index", "sha256": "<64 hex>", "size": 18},
    {"path": "Report (released).pdf", "role": "document", "sha256": "<64 hex>", "size": 10}
  ],
  "format": "ogentic-audit-release/v1",
  "key_id": "<64 hex>",
  "logs": [
    {"checkpoint": {"alg": "ed25519", "head_ts_wall": "…", "key_id": "<64 hex>", "log_id": "<64 hex>",
                    "record_count": 42, "record_hash": "<64 hex>", "record_id": 41, "segment": 0},
     "path": "Audit log"}
  ],
  "release_id": "<text>"
}
```

(Pretty-printed for reading; the file itself is canonical, single-line, §3.6.)

| Field | Rule |
|-------|------|
| `format` | `"ogentic-audit-release/v1"` |
| `alg`, `key_id` | the attestation signer; `key_id` MUST equal the SSHSIG key's fingerprint |
| `release_id` | caller-defined text, 1–256 characters |
| `created_at` | RFC 3339 UTC, millisecond precision, `Z` (the signer's clock) |
| `files[]` | every released file; sorted by `path` bytes; `path` unique |
| `files[].size`, `.sha256` | byte length and SHA-256 of the file |
| `files[].role` | optional caller-defined text (e.g. `document`, `index`, `decisions`, `instructions`). Opaque to the verifier |
| `files[].parts[]` | optional byte ranges naming the items inside a file (pages, index rows, per-item decision entries): sorted by `offset`, non-overlapping, `length ≥ 1`, inside `size`, `name` unique within the file |
| `logs[]` | every audit log in the bundle, sorted by `path`; `checkpoint` is the §10.1 object without `format` and `observed_at` |

**Paths.** Relative, `/`-separated, UTF-8 in Unicode NFC; no empty, `.`, or `..` components; no leading `/`; no `\` or NUL; not a reserved bundle entry or inside one; not a segment file (`audit-NNNN.cbor`) of a listed log (other files inside a log directory, such as instructions, may be listed).

**What goes in.** A per-item decision index (for example every page hash and every withholding decision) is a released file, with one part per item. That gives a byte change inside it an item-level name. The decisions themselves are also records in the audit log, whose head the attestation pins. **Everything in the attestation is published in the clear**: paths, roles, and part names MUST NOT contain withheld information, and files that were not released MUST NOT be listed.

### 11.3 Signing

`signature = SSHSIG(namespace "ogentic-audit/v0.2/release", message = the attestation file bytes)`. The signer is normally the log signer. Each `logs[].checkpoint.key_id` MAY differ (for example a log written before a rotation), and every such key must itself be trusted when verified.

### 11.4 `verify-release` algorithm

```
ogentic-audit verify-release <dir> (--public-key K | --key-fingerprint F | --trust FILE)
                             [--revocations FILE]… [--statements DIR]… [--strict] [--format json]
```

Unlike a log, a release's items are independent, so the verifier checks **every** item and reports **all** violations. The first in this order is the headline. A failure at A1–A5 ends the run, because comparing files against an attestation that is not authenticated proves nothing. With no pin at all, A3 is skipped and the run continues to a best verdict of `SelfConsistent`.

| # | Step | Failure → kind | Item |
|---|------|----------------|------|
| A1 | attestation file present | `AttestationMissing` | `attestation` |
| A2 | `.sig` present and parses (§3.3) | `SignatureInvalid` (`missing`, `malformed`, `namespace`, `hash_alg`, `key_type`) | `attestation` |
| A3 | SSHSIG key trusted (§9.5), not revoked | `UntrustedSigner` / `RevokedKey` (no trust context → verdict at best `SelfConsistent`) | `attestation` |
| A4 | signature verifies strictly over the file bytes | `SignatureInvalid` | `attestation` |
| A5 | canonical JSON, schema, path rules, `key_id` == SSHSIG key | `AttestationMalformed` (`KeyIdMismatch` for the last) | `attestation` |
| F1 | each `files[]` entry exists (lookup by NFC name; §11.5) | `FileMissing` | `file:<path>` |
| F2 | it is a regular file reached without following a symlink | `FileAltered` (`not_regular_file`) | `file:<path>` |
| F3 | `size` and `sha256` match. On mismatch the reason is `size` if the length differs; otherwise `part`, naming the first declared part whose hash differs; otherwise `outside_parts` (every part matches) or `content` (no parts declared) | `FileAltered` | `file:<path>` or `file:<path>#<part>` |
| L1 | each `logs[]` directory exists | `FileMissing` | `log:<path>` |
| L2 | §8 verification of that log, same trust context | any §8.3 kind | `log:<path>/s<N>r<P>` |
| L3 | the log contains the attested checkpoint (§10.3 steps 2–4; a different `log_id` is `CheckpointMismatch` here, because the attestation is evidence, not operator input) | `CheckpointTruncated` / `CheckpointMismatch` | `log:<path>/s<N>r<P>` |
| U1 | files not covered: not listed, not a segment file of a listed log, not a reserved bundle entry | listed as **unattested** (warning); with `--strict`, `UnattestedFile` | `file:<path>` |

Records after the attested head (signed by a trusted key) are reported as a count and are not a failure. Unattested files never fail by default: operating systems add files (`.DS_Store`, `Thumbs.db`) when a folder is browsed. The human report lists them by name under "not covered by the attestation", so an added file can never pass as released.

### 11.5 Name lookup

The verifier enumerates the release directory once, without following symlinks, and maps each entry's NFC-normalized relative path to the entry. Attested paths are looked up by NFC equality, so a bundle that passed through a filesystem that stores names decomposed (NFD) still verifies. Two entries with the same NFC path make that path ambiguous: `FileAltered` (`ambiguous_name`). It fails closed.

### 11.6 Report and verdicts

As §8.5, with the release-level JSON `{"format":"ogentic-audit-release-report/v1","verdict":…,"release_id":…,"signer":{…},"files":{"attested":n,"verified":n,"unattested":[…]},"logs":[<§14 report>…],"violations":[…]}`. Compact verdicts: `Verified`, `SelfConsistent`, `<Kind>@attestation`, `<Kind>@file:<path>`, `<Kind>@file:<path>#<part>`, `<Kind>@log:<path>/s<N>r<P>`.

Human output names the item:

```
✗ Verification failed · FileAltered · "Index.csv" · part "row 1" (bytes 14–17)
! Self-consistent, signer not pinned · signed by 6db5 e9b8 a1ba ce1c dd9a 7c6a db9e 9396 acc5 0734 65d9 fe8e 3a0e f6d9 c60d 6d4f
  Obtain the signer's fingerprint independently and re-run with --key-fingerprint.
✓ Verified · release "…" · 14 files · 1 audit log (2 segments, 1,207 records) · signer pinned (6db5 e9b8 …)
```

### 11.7 Checking a release with stock tools only

The signature and the released files can be checked with no `ogentic-audit` software at all, using OpenSSH ≥ 8.1, `shasum`, and `jq` (or `python3`). That is an implementation independent of ours:

```sh
# 1. Pin: one line, built from the key you obtained independently.
echo 'release-signer ssh-ed25519 AAAA…' > allowed_signers

# 2. The attestation is signed by that key, for this purpose.
ssh-keygen -Y verify -f allowed_signers -I release-signer \
  -n ogentic-audit/v0.2/release \
  -s ogentic-audit-release.json.sig < ogentic-audit-release.json

# 3. Every released file matches; an altered file prints FAILED with its name.
jq -r '.files[] | "\(.sha256)  \(.path)"' ogentic-audit-release.json | shasum -a 256 -c
```

This path was exercised end to end against a hand-built attestation (RFC 8032 key, non-ASCII file names, one byte appended to one file: `ssh-keygen` returns 0 for the original, `shasum` prints `FAILED` for the altered file). It does not check `parts` or the audit-log chain. For the chain, use the `ogentic-audit` CLI or Python package, or an independent implementation of §8.

## 12. Downgrade and confusion rules (summary)

1. A signed-mode verification of an HMAC (`0x0001`) log or segment is `FormatDowngrade`, never an HMAC verification.
2. An HMAC-mode verification of a signed log is an argument error, never a silent pass.
3. A log never mixes formats, algorithms, or keys (H3, H10).
4. `sig_alg` is inside every signed record and every hashed header. The key type is inside `key_id` and every SSHSIG. The verifier checks they agree and never infers an algorithm.
5. Namespaces separate records, checkpoints, attestations, transitions, and revocations.
6. Only `sha512` SSHSIGs, strict Ed25519, no weak keys.
7. v1 and v2 checkpoints are not interchangeable.

## 13. Library and CLI surface (informative)

Rust (`ogentic-audit-core`, additive; enums gaining variants become `#[non_exhaustive]`):

- `SigAlg`, `PublicKey` (`parse` from any §3.7 form; `to_openssh(comment)`, `to_pem()`, `to_hex()`), `Fingerprint` (`to_grouped_hex()`, `to_openssh()`, `parse`).
- `trait Signer: Send + Sync { fn public_key(&self) -> &PublicKey; fn sign(&self, namespace: &str, message: &[u8]) -> Signature; }`. `InMemorySigner::from_seed([u8; 32])` and `generate()`, zeroized on drop.
- `Writer::open_signed(dir, Box<dyn Signer>, session_id)`.
- `TrustContext` (pins, statements, revocations; `from_allowed_signers`), `SignedVerifier::new(TrustContext).verify_with_options(dir, opts)`. The report adds `Verdict::SelfConsistent` and a `signer` block.
- `checkpoint::v2::{make, sign, verify}`, `release::{AttestationBuilder, sign, verify_release}`, `statements::{transition, revocation}`.
- `FORMAT_VERSION` stays `0x0001`. `FORMAT_VERSION_SIGNED = 0x0002` is added.

`ogentic-audit-keychain`: `KeychainSigner::{load, load_or_generate, delete}(service, account)`. The 32-byte Ed25519 seed is stored as a generic password **tagged** `ed25519-seed:v1:` plus the seed, so a signing seed can never be loaded as an HMAC key or the reverse (the HMAC loader requires exactly 32 bytes). The item MUST be device-only (not synced). Public key and fingerprint are readable without exporting the seed.

Python (`ogentic_audit`): `SigningKey.generate() / from_seed() / from_keychain()`, `.public_key_openssh(comment)`, `.fingerprint()` (grouped hex), `.fingerprint_openssh()`; `Writer.open(dir, signing_key=…)`; `verify(dir, public_key=… | key_fingerprint=… | trust=…, checkpoint=…)` returning a report whose `.verdict` is `"Verified" | "SelfConsistent" | "Violation"` and whose `.ok` is true **only** for `Verified`; `checkpoint(dir, signing_key=None)`; `attest_release(dir, files, logs, signing_key)`; `verify_release(dir, …)`. The existing `verify(dir, key=KeyHandle)` is unchanged.

CLI (`ogentic-audit`): `verify` auto-detects the format (§8.1) and adds `--public-key`, `--key-fingerprint`, `--trust`, `--revocations`, `--statements`; `verify-release`; `checkpoint` writes v2 for signed logs (`--sign` to sign); `key generate | export [--format openssh|pem|hex] | fingerprint | transition | revoke`; `show` and `head` read both formats.

## 14. Report format, `format_version` 2

[`violation-report.md`](violation-report.md) applies, with these changes for v0.2 logs:

- `format_version: 2`; `verdict` adds `"SelfConsistent"`.
- `log.final_hmac_hex` is replaced by `log.final_record_hash_hex`; `log.log_id_hex` is added.
- A `signer` block: `{ "alg", "key_id_hex", "fingerprint_openssh", "trusted": bool, "trust_path": [key_id_hex…], "reason": "pinned" | "transition" | "not_pinned" | "no_signed_records" }`.
- A `checkpoint` block when one was supplied: `{ "signed": bool, "signer_key_id_hex" | null }`.
- New kinds: `SignatureInvalid` (`reason`: `missing`, `malformed`, `namespace`, `hash_alg`, `key_type`, `noncanonical`, `weak_key`, `mismatch`), `UntrustedSigner` (`expected`: pinned fingerprints; `actual`: signer fingerprint), `RevokedKey`, `AlgorithmMismatch`, `UnsupportedAlgorithm`, `FormatDowngrade` (`expected_version`, `actual_version`), and for releases `AttestationMissing`, `AttestationMalformed`, `FileMissing`, `FileAltered` (`reason`: `size`, `part`, `outside_parts`, `content`, `not_regular_file`, `ambiguous_name`; `expected_sha256`, `actual_sha256`, `expected_size`, `actual_size`, `part` {`name`, `offset`, `length`} or null), `UnattestedFile`.
- `HmacMismatch` does not occur for v0.2 logs.

`ts_wall`, `head_ts_wall`, `observed_at`, `created_at` are all the signer's clock. A report never presents them as independently established time. Trusted time (an RFC 3161 token over a checkpoint or attestation) is a later, additive artefact.

## 15. Post-quantum

`sig_alg 0x0002` is reserved for ML-DSA-65 (FIPS 204) and is **not implemented**. When it is: header `P` = 1952, signature 3309 bytes, a key type string for SSHSIG and fingerprints is fixed, and golden vectors are added. Nothing else in this spec changes, because every byte layout is parameterized by `sig_alg`. Until then, the long-term defense for evidence made today is a checkpoint or attestation held by others (and, optionally, timestamped) **before** Ed25519 could be forged. A log or attestation created after that point proves nothing by its Ed25519 signature alone.

## 17. Versioning and compatibility

- Format `0x0001` is frozen and keeps working in every API, the CLI, and the Python package, with unchanged exit codes and report shape (`format_version: 1`).
- Format `0x0002` is a separate mode selected by the writer at log creation. There is no in-place conversion. Re-signing an HMAC log would make the new key vouch for history it never witnessed.
- Library versions: the release that implements this spec is **0.4.0** for every crate and the Python package, because `ViolationKind` and `Verdict` gain variants (they become `#[non_exhaustive]` in the same release). No existing function changes signature.
- Reserved: `sig_alg` values (§3.2), record keys ≥ 100, header `reserved`, and the `attestation` record field named in ADR-0001 (still unassigned; external witnessing is done with signed checkpoints, §10.1).
