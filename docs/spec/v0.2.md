# ogentic-audit — On-disk format spec, v0.2 (signed mode)

**Status:** Draft (depends on [ADR-0004](../adr/0004-signed-chain-and-offline-verification.md)). Normative once ADR-0004 is Accepted and the v0.2 golden vectors are committed.
**Last updated:** 2026-10-03 (revised after a cryptographic review and a compatibility review)
**Format version:** `0x0002`. Format `0x0001` ([v0.1](v0.1.md), HMAC-SHA256) is unchanged and remains a valid, supported mode.

v0.2 adds a **signed** format in which the party that writes the log and the party that verifies it can be different principals. Every record carries an Ed25519 signature; records are linked by a public SHA-256 hash; verification needs only the signer's **public** key. Nobody who verifies a v0.2 log can forge one.

This document specifies, byte for byte:

1. the signed log format: segment header, record framing with a detachable body, record schema, chain, and sealing;
2. **signed checkpoints** and **witness co-signatures**;
3. **release attestations**: a signed index of every file in a release and of every audit-log head, verifiable offline with our software or with stock tools only;
4. **trust**: pins and their scopes, key transitions (rotation), revocations, and how they combine;
5. the **verification algorithm**: every failure mode, the report kind it produces, and what a person reading the output is told.

Everything not restated here is inherited from [v0.1](v0.1.md): canonical CBOR rules, timestamp rules, payload conventions, crash-recovery framing.

## 1. Goals and non-goals

**Goal.** A third party (a requester, an auditor, a court) holding a log or a release can establish the following without any secret and without the writing application installed. They need a public key obtained **outside** that log or release, and a verifier also obtained outside it (§11.8), or only the stock tools of §11.7:

- every record was produced by the holder of the matching private key, and that key was trusted for that purpose (§9);
- no record was altered, removed, reordered, or inserted up to a head the report names, and whether anything could have been cut after that head (§8.5, *anchored*);
- every attested file in a release is byte-identical to what the signer released. A changed file, page file, or index row is named;
- the audit-log heads are the ones the signer released with it.

A release may withhold content. Records whose content is withheld are carried with their bodies **elided** (§5). Values derived from withheld content are **commitments**, not plain hashes (§6.3). The chain still verifies.

**Non-goals.**

- Confidentiality of the writer's own log. Records are plaintext on the writer's disk (see v0.1). A release controls what it discloses through elision.
- Trusted time. `ts_wall`, `observed_at` and `created_at` are the signer's clock (§14).
- Multiple concurrent writers on one log.
- Detecting a signer who rewrites their own log when nobody holds an earlier checkpoint (§10.5). The defense is checkpoints, not the format.
- Naming a page inside a multi-page file. Page-level naming needs one file per page (§11.2).

## 3. Cryptography

### 3.1 Primitives

A conforming v0.2 verifier needs exactly:

- **Ed25519** (with SHA-512, as RFC 8032 defines), with the point checks of §3.5;
- **SHA-256**;
- **CRC32**, for corruption detection only, never security;
- canonical **CBOR** (v0.1 rules) and canonical **JSON** (§3.6);
- **base64** (RFC 4648 §4).

It does **not** need HMAC, BLAKE3, or any secret. Ed25519 and SHA-256 are provided by OpenSSH, Go `crypto/ed25519`, Node `crypto`, OpenSSL ≥ 1.1.1, and Python `cryptography`. **None of these applies all of §3.5.** OpenSSH accepts `S ≥ L`. Both OpenSSH and OpenSSL accept signatures under small-order keys. An implementation built on them adds the missing checks itself.

### 3.2 Algorithm identifiers

| `sig_alg` (u16) | JSON `alg` | SSH key type | Public key | Signature | Status |
|---|---|---|---|---|---|
| `0x0000` | — | — | — | — | invalid |
| `0x0001` | `"ed25519"` | `ssh-ed25519` | 32 B | 64 B | **defined** |
| `0x0002` | `"ml-dsa-65"` | none yet (§15) | 1952 B | 3309 B | **reserved** (FIPS 204) |
| others | — | — | — | — | unassigned |

The algorithm identifier is bound into every signed byte string: into each record envelope (key 12), into the segment header (hashed into the chain start), into the key blob (and therefore `key_id`), and into every SSHSIG (key type and signature type strings). Every JSON object that carries `alg` MUST name the type of the key that signs it. A verifier MUST check that all of them agree. It never infers the algorithm from a length.

Strength order: `0x0001` < `0x0002`. A transition never goes to a weaker algorithm (§9.3).

### 3.3 Signatures: SSHSIG with a namespace

Every signature in v0.2 is an Ed25519 signature over the **SSHSIG signed data** defined by OpenSSH [`PROTOCOL.sshsig`](https://github.com/openssh/openssh-portable/blob/master/PROTOCOL.sshsig):

```
signed_data(namespace, message) =
    "SSHSIG"                      (6 ASCII bytes, no length prefix)
  ‖ string(namespace)
  ‖ string("")                    (reserved, empty)
  ‖ string("sha512")
  ‖ string(SHA-512(message))
signature = Ed25519-Sign(private_key, signed_data(namespace, message))
```

We invent no signature construction. SSHSIG is a published, deployed domain-separation scheme, and it makes every detached signature in this spec checkable with `ssh-keygen -Y verify` (OpenSSH ≥ 8.1).

| Namespace | Signs | Message | Signed by (the key the object names) |
|-----------|-------|---------|--------------------------------------|
| `ogentic-audit/v0.2/record` | a log record | the record's `envelope_bytes` | the segment header's key |
| `ogentic-audit/v0.2/checkpoint` | a checkpoint (§10.1) | the file bytes | `key_id` |
| `ogentic-audit/v0.2/witness` | a witness co-signature (§10.2) | the file bytes | `witness_key_id` |
| `ogentic-audit/v0.2/release` | a release attestation (§11) | the file bytes | `key_id` |
| `ogentic-audit/v0.2/key-transition` | a key transition (§9.3) | the file bytes | `old_key_id` |
| `ogentic-audit/v0.2/key-transition-accept` | the new key's acceptance of a transition (§9.3) | the same file bytes | `new_key_id` |
| `ogentic-audit/v0.2/key-revocation` | a revocation (§9.4) | the file bytes | `revoker_key_id` |

A signature valid in one namespace is invalid in every other, so no signed object can be replayed as another kind.

**Who signed a detached object.** The signer of a detached object is the key the object itself names (last column). A key is never trusted because it appears in an SSHSIG blob. The verifier:

1. parses the blob strictly (below);
2. requires the blob's key to be authorised for this object: trusted with this namespace in its scope (§9.1, §9.5), and allowed to sign this object at all (retirement §9.3, revocation authority and cut points §9.4). The one exception is a transition's acceptance signature, whose key need not be trusted yet: it MUST be the transition's `new_key_id` (§9.3);
3. verifies the signature (§3.5) under that key;
4. parses the object (§3.6);
5. requires the object's signer field to equal the blob key's `key_id`.

An implementation MUST look the key up by the object's signer field and verify under the trusted copy. It never trusts a key because it appears in a blob. An object whose signer field names a different key from the one that signed it is rejected, whatever the signature says. For an attestation that is `KeyIdMismatch`. For a checkpoint or a statement passed in by the operator it is an argument error. For a statement found in a bundle it is ignored with a warning. Together, steps 2–5 establish that the key the object names made the signature and is authorised for this purpose. Golden vectors include a statement signed by a stranger that claims to come from the pinned key (§16).

**On disk.** Inside a log, only the raw 64-byte signature is stored; the key and namespace are implied. **Detached signatures** (checkpoints, witness co-signatures, attestations, statements) are stored as the full armored SSHSIG blob in a sibling file named `<file>.sig`. A transition's acceptance is stored as `<file>.accept.sig`.

```
blob =
    "SSHSIG"
  ‖ uint32(1)                                   (SIG_VERSION)
  ‖ string(key blob)
  ‖ string(namespace)
  ‖ string("")
  ‖ string("sha512")
  ‖ string( string("ssh-ed25519") ‖ string(signature) )

armored =
    "-----BEGIN SSH SIGNATURE-----\n"
  ‖ base64(blob), wrapped at 70 characters per line, each line ending "\n"
  ‖ "-----END SSH SIGNATURE-----\n"
```

Writers MUST emit exactly this armor, which is what `ssh-keygen -Y sign` emits. Readers MUST accept any line length and ignore `\r`.

**Strict parsing.** A verifier MUST reject a blob unless all of these hold:

- the magic is `SSHSIG` and the version is 1;
- every `string` length lies within the bytes remaining at that level;
- the key blob is exactly `string("ssh-ed25519") ‖ string(32 bytes)`, and the signature blob exactly `string("ssh-ed25519") ‖ string(64 bytes)`, each consumed with no bytes left over;
- the namespace equals the one the object type requires, the reserved field is empty, and the hash algorithm is `sha512`;
- nothing follows the signature blob;
- the armored file is within the size limit of §3.8.

For a release attestation, rejection is the violation `SignatureInvalid`, with reason `malformed`, `namespace`, `hash_alg`, or `key_type`. For a checkpoint or a revocation passed in by the operator it is an error (§8.4). For a statement found in a bundle it is a warning (§9.2). (`ssh-keygen` also accepts `sha256`. v0.2 writers never produce it and v0.2 verifiers reject it, so each signature has one encoding.)

### 3.4 Hashes with domain separation

```
TH(tag, data) = SHA-256( tag ‖ 0x00 ‖ data )
```

| Tag (ASCII, no NUL) | Input | Output |
|---------------------|-------|--------|
| `ogentic-audit/v0.2/header` | segment header bytes, CRC excluded | `chain_start` |
| `ogentic-audit/v0.2/record` | record `envelope_bytes` | `record_hash` |
| `ogentic-audit/v0.2/body` | record `body_bytes` | `body_hash` |
| `ogentic-audit/v0.2/commit` | `nonce` (32 bytes) ‖ value | commitment |

`key_id` is the one untagged hash: `SHA-256(key blob)`, so that it equals the OpenSSH fingerprint. A key blob begins `00 00 00 0b`, which no tagged input can.

### 3.5 Strict verification

This section defines Ed25519 verification completely, so conformance does not depend on any one library. Let `p = 2^255 − 19`, `L = 2^252 + 27742317777372353535851937790883648493`, and `B` the base point. A signature is `R_bytes ‖ S_bytes` (32 + 32 bytes) on message `M` under public key `A_bytes`.

1. **Canonical encodings.** `A_bytes` and `R_bytes` each decode to a point on the curve, and re-encoding that point gives back exactly the same 32 bytes (compared as bytes). This rejects `y ≥ p`, points not on the curve, and `x = 0` with the sign bit set.
2. **No small-order points.** Neither `A` nor `R` is one of the 8 points whose order divides 8. [Appendix A](#appendix-a-small-order-encodings) lists all 14 byte strings that a lax decoder maps to those points; rule 1 already rejects the 6 non-canonical ones.
3. **Torsion-free keys.** `[L]A` is the identity. This rejects a key with a small-order component even when the key itself is not of small order. It is checked once per key: when the key is pinned, when it is read from a segment header, and when an SSHSIG blob key is accepted against a fingerprint pin. Every verification key therefore passes it.
4. **Canonical `S`.** `S`, read little-endian from `S_bytes`, is less than `L`.
5. **The equation, cofactorless, compared as bytes.** `k = SHA-512(R_bytes ‖ A_bytes ‖ M) mod L`. Compute `R' = [S]B − [k]A`. The signature is valid if and only if `encode(R') = R_bytes`.

**Cofactored verification** (`[8][S]B = [8]R + [8][k]A`) is **non-conforming**. It accepts `R + T` for a small-order `T`, which the cofactorless rule rejects. A signer who later wanted deniability could exploit that disagreement between implementations. Rules 1–5 are what `ed25519-dalek` 2.x `verify_strict` does, plus the explicit canonical-encoding check of rule 1 and the torsion check of rule 3. An implementation on another library adds whichever of rules 1–4 that library omits.

| Failure | `SignatureInvalid` reason | What the report says |
|---------|---------------------------|----------------------|
| `A` fails rule 1, 2 or 3 | `weak_key` | "the signing key is one under which anyone can make signatures" |
| `S ≥ L`, and the signature is valid with `S mod L` | `reencoded` | "a valid signature, re-encoded after signing: the signed content is unchanged, but someone changed the signature bytes afterwards". Anyone can do this without the key |
| anything else | `mismatch` | "the signature does not match the signed content" |

A **pinned** key that fails rule 1, 2 or 3 is refused when it is pinned (argument error, exit 3).

**Where stock tools differ, exactly.** These were tested with OpenSSH 10.3 and Python `cryptography` (OpenSSL):

- OpenSSH accepts a signature whose `S` was replaced by `S + L`. OpenSSL rejects it.
- Both accept an all-zero `S` with `R` the identity, under the identity key, for **any message**.

Consequences:

- The stock-tools path (§11.7) is sound only for a pin that is not a weak key. Its recipe checks the pin against Appendix A before anything else.
- Re-encoding is the one case where `ssh-keygen` passes and `ogentic-audit` fails on the same bundle. The report names it `reencoded`, so the two results differ for a stated reason instead of contradicting each other.
- A verifier built on OpenSSL or OpenSSH, including the vector generator's oracle (§16), checks rules 1–3 itself.

### 3.6 Canonical JSON

Checkpoints, witness co-signatures, attestations, and key statements are JSON documents in **canonical form**: [RFC 8785 (JCS)](https://www.rfc-editor.org/rfc/rfc8785) restricted to this subset, under which JCS is trivial to reproduce:

- values are objects, arrays, strings, or integers in `[0, 2^53 − 1]`. No floats, negatives, booleans, or `null`;
- object keys are ASCII, sorted by byte order, with no duplicates;
- optional members are **omitted**, never `null`;
- no whitespace outside strings. Strings are UTF-8, escaping only `"`, `\`, and U+0000–U+001F (as `\b \f \n \r \t`, or `\u00xx` with lowercase hex);
- the file is exactly the canonical bytes: no BOM, no trailing newline.

Python's `json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)` produces this form for the subset. A verifier MUST parse the file, re-serialize it canonically, and reject the document if the bytes differ (`AttestationMalformed`, or an argument error for a pin or statement file). This closes parser differentials (duplicate keys, alternative escapes) between our verifier, `jq`, and any third party's parser: there is one byte string per document.

**Numbers are type-checked.** A parsed `1.0` round-trips byte for byte through both Python's `json` and `serde_json`, so the re-serialization check does not exclude it. The schema check does: every numeric field MUST be an integer. Nesting depth and sizes are capped (§3.8).

### 3.7 Public key formats and fingerprints

**Export formats.** All are equivalent, and a verifier accepts each wherever a public key is expected:

| Format | Example (RFC 8032 §7.1 TEST 1 key) |
|--------|---------|
| OpenSSH line (default) | `ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAINdamAGCsQq31Uv+08lkBzoO4XLz2qYjJa8CGmj3B1Ea <comment>` |
| PEM SubjectPublicKeyInfo ([RFC 8410](https://www.rfc-editor.org/rfc/rfc8410)) | `-----BEGIN PUBLIC KEY-----` / `MCowBQYDK2VwAyEA11qYAYKxCrfVS/7TyWQHOg7hcvPapiMlrwIaaPcHURo=` / `-----END PUBLIC KEY-----` |
| Raw hex | `d75a980182b10ab7d54bfed3c964073a0ee172f3daa62325af021a68f707511a` |

**Fingerprint text forms** of the same 32 `key_id` bytes:

| Form | Use | Example |
|------|-----|---------|
| Grouped hex | Reading aloud, printing on letters and web pages | `6db5 e9b8 a1ba ce1c dd9a 7c6a db9e 9396 acc5 0734 65d9 fe8e 3a0e f6d9 c60d 6d4f` |
| Dashed hex | Command lines (one shell argument, no quotes needed) | `6db5-e9b8-a1ba-ce1c-dd9a-7c6a-db9e-9396-acc5-0734-65d9-fe8e-3a0e-f6d9-c60d-6d4f` |
| OpenSSH | Cross-checking with `ssh-keygen -l -f key.pub` | `SHA256:bbXpuKG6zhzdmnxq256TlqzFBzRl2f6OOg722cYNbU8` |

Grouped hex is the primary human form: 16 groups of 4 characters from a 16-symbol, case-insensitive alphabet, unambiguous over a phone line. The full 256 bits are always shown. There is no short form, so nobody pins a truncation. The example values were cross-checked with OpenSSH 10.3 (`ssh-keygen -l`).

**Parsing.** A parser removes spaces, `-` and `:`. What remains MUST be exactly 64 hex digits (either case), or a `SHA256:` value whose base64 decodes to exactly 32 bytes. Anything else, including 63 or 65 hex digits, is an argument error (exit 3). Fingerprints are always compared in full. An implementation never matches a prefix or a suffix.

**Compare by machine, not by eye.** Someone with enough computing power can generate a key whose fingerprint shares chosen first and last groups with yours, and those are the groups people check by eye. Pass the fingerprint to `--key-fingerprint`, or use the shell comparison in §11.7, step 1.

### 3.8 Limits on untrusted input

Every input below can come from an untrusted holder. Limits apply before parsing:

| Input | Limit | Over the limit |
|-------|-------|----------------|
| record envelope (`len_prefix`) | ≤ 4096 bytes | `RecordCorrupt` (`TooLarge`) at that record, before any parse or signature check. A length within the limit that runs past the end of the file is an incomplete record (what a crash leaves): `RecordCorrupt` (`TornTail`), as v0.1 |
| record body (`body_len`) | ≤ the bytes remaining in the file | the record is incomplete: `RecordCorrupt` (`TornTail`), as v0.1 |
| detached `.sig` file | ≤ 64 KiB | `SignatureInvalid` (`malformed`) |
| release attestation | ≤ 64 MiB; ≤ 1,048,576 files; ≤ 1,048,576 parts in total; ≤ 1024 logs | `AttestationMalformed` (`limit`) |
| any JSON document | no deeper than its schema (at most 5 levels) | `AttestationMalformed`, or an argument error for operator input |
| key statements | ≤ 1024 per run, each ≤ 16 MiB | argument error when passed by the operator; ignored with a warning when found in a bundle |
| trust file | ≤ 1 MiB and ≤ 1024 keys | argument error |

Hashes over files and messages are computed while reading. No released file or segment is held in memory whole. Trust evaluation (§9.5) terminates after at most one pass per statement.

## 4. Segment header

Segment files keep v0.1 naming (`audit-NNNN.cbor`, §7). The header length depends on `sig_alg`: `H = 96 + P`, where `P` is the public-key length (Ed25519: `P = 32`, `H = 128`).

| Offset | Length | Field | Notes |
|--------|--------|-------|-------|
| 0 | 4 | `magic` | ASCII `"OGAU"` |
| 4 | 2 | `version` | u16 LE, `0x0002` |
| 6 | 2 | `segment_index` | u16 LE; MUST equal the index in the file name |
| 8 | 2 | `sig_alg` | u16 LE (§3.2) |
| 10 | 2 | `reserved` | zero |
| 12 | 16 | `log_id` | random, from the OS CSPRNG when the log is created; identical in every segment of the log |
| 28 | 32 | `key_id` | `SHA-256(key blob)` of `public_key` |
| 60 | 32 | `prev_final` | segment 0: 32 zero bytes; segment N ≥ 1: `record_hash` of the last record of segment N−1 |
| 92 | `P` | `public_key` | the signer's public key: **informational until pinned** (§9) |
| 92+`P` | 4 | `header_crc` | u32 LE, CRC32 (IEEE 802.3) of bytes `[0, 92+P)` |

```
chain_start_N = TH("ogentic-audit/v0.2/header", header_N[0 .. 92+P))
```

Every segment's header, not only segment 0's, is hashed into its `chain_start`, which record 0 of that segment signs as its `prev_hash`. The whole header (index, algorithm, `log_id`, key, continuity link) is therefore covered by a signature as soon as the segment has a record.

`log_id` is chosen at random rather than derived from the log's content, so it stays the same if the history is rewritten. A checkpoint against a rewritten log then reports the rewrite (`CheckpointMismatch`), and two logs never share an id.

**Older readers.** A v0.1 reader checks `version` before the CRC, so it never misparses a v0.2 segment. It does misreport one: `ogentic-audit` 0.3.x reports a v0.2 segment as an `UnknownVersion` **violation** (exit 1, status `"tampered"`), and it has no `verify-release` subcommand (its argument parser exits 2). Verification instructions therefore say "requires ogentic-audit 0.4.0 or later" (§11.9).

From 0.4.0, a segment 0 whose version is higher than any the verifier implements is an argument error: "this log uses format 0x000N; upgrade the verifier" (exit 3), never a violation. A version that is not higher (such as `0x0000`) is still `UnknownVersion`. Input in format `0x0001` is unaffected.

**Example.** Genesis header for the RFC 8032 TEST 1 key with `log_id` `000102030405060708090a0b0c0d0e0f` (128 bytes):

```
0000  4f 47 41 55 02 00 00 00 01 00 00 00 00 01 02 03
0010  04 05 06 07 08 09 0a 0b 0c 0d 0e 0f 6d b5 e9 b8
0020  a1 ba ce 1c dd 9a 7c 6a db 9e 93 96 ac c5 07 34
0030  65 d9 fe 8e 3a 0e f6 d9 c6 0d 6d 4f 00 00 00 00
0040  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
0050  00 00 00 00 00 00 00 00 00 00 00 00 d7 5a 98 01
0060  82 b1 0a b7 d5 4b fe d3 c9 64 07 3a 0e e1 72 f3
0070  da a6 23 25 af 02 1a 68 f7 07 51 1a 52 2d 04 b2
chain_start_0 = 377d85f15f810e761308e18230717c9b7a58554a611ef77df2a5822e1fd977dc
```

**One key per log.** Every segment of a log MUST carry the same `sig_alg`, `log_id`, `key_id`, and `public_key` as segment 0. Rotation starts a new log (§9.3); it never changes the key inside one (ADR-0004 D8).

## 5. Record framing

| Length | Field | Notes |
|--------|-------|-------|
| 4 | `len_prefix` | u32 LE, length of `envelope` (≤ 4096, §3.8) |
| `len_prefix` | `envelope` | canonical CBOR map (§6.1) |
| `S` | `signature` | raw signature over the envelope; `S` from §3.2 (Ed25519: 64) |
| 4 | `body_len` | u32 LE; `0` means the body is elided |
| `body_len` | `body` | canonical CBOR map (§6.2) |
| 4 | `len_trailer` | u32 LE, MUST equal `len_prefix` |

```
signature_n   = Ed25519-Sign(sk, signed_data("ogentic-audit/v0.2/record", envelope_bytes_n))
record_hash_n = TH("ogentic-audit/v0.2/record", envelope_bytes_n)
body_hash_n   = TH("ogentic-audit/v0.2/body", body_bytes_n)      (stored in the envelope, key 13)
```

The signature and the chain cover the envelope, and the envelope covers the body through `body_hash`. The body can therefore be removed (**elided**) without breaking either: the signature still verifies and the chain still links. A body that is present MUST hash to `body_hash`, so one changed byte in a body is reported at that record (`SignatureInvalid`, reason `body_mismatch`).

`record_hash` covers the envelope, not the signature. Record identity is therefore independent of signature encoding, and a checkpoint pins content, not a signature byte string.

**Eliding.** Only a release builder elides, and only in the copy it puts in a release (§11.3). A writer never writes an elided record. Every report counts elided records and lists their positions. Structural records (`segment.finalized`, `log.sealed`, `log.continued`) MUST NOT be elided, because the verifier checks their payloads: an elided structural record is `RecordCorrupt` (`ElidedStructural`).

## 6. Record schema

### 6.1 Envelope

A CBOR map with integer keys, canonical per v0.1 §"Canonical encoding rules". Key numbers follow v0.1 where the field is the same.

| Key | Field | Type | v0.2 rule |
|-----|-------|------|-----------|
| 1 | `record_id` | uint | MUST equal the record's position in its segment (0, 1, 2, …) |
| 2 | `prev_hash` | bstr 32 | record 0 of segment N: `chain_start_N`; otherwise the preceding record's `record_hash` |
| 3 | `ts_wall` | tstr | as v0.1 |
| 4 | `ts_mono_delta` | uint | as v0.1 |
| 5 | `session_id` | bstr 16 | as v0.1 |
| 7 | `event` | tstr | 1–128 bytes of printable ASCII (0x21–0x7E), from the application's fixed vocabulary of event names. It stays visible when the body is elided, so it MUST NOT carry content |
| 9 | `key_id` | bstr 32 | MUST equal header `key_id` |
| 10 | `schema_version` | uint (u8) | as v0.1 |
| 11 | `segment_index` | uint (u16) | MUST equal header `segment_index` |
| 12 | `sig_alg` | uint (u16) | MUST equal header `sig_alg` |
| 13 | `body_hash` | bstr 32 | `TH("ogentic-audit/v0.2/body", body_bytes)` |

All eleven keys are required. Keys 6, 8, and 14–99 MUST be rejected in an envelope. Keys ≥ 100 stay reserved for additive optional fields, as in v0.1. Each envelope thus names its own position, log key, and algorithm inside the signed bytes, so a record extracted on its own (into an exhibit or a checkpoint) still says how to check it.

### 6.2 Body

| Key | Field | Type | Rule |
|-----|-------|------|------|
| 6 | `actor` | tstr | as v0.1 |
| 8 | `payload` | map | as v0.1 (text keys) |
| 14 | `nonce` | bstr 32 | fresh from the OS CSPRNG for every record |

All three keys are required; any other key MUST be rejected. The nonce makes `body_hash` a hiding commitment: an elided body cannot be confirmed by guessing its contents.

### 6.3 Payload conventions

Payload conventions carry over from v0.1, with these changes and additions:

- **`segment.finalized`**: `payload` is `{ "records": uint, "final_hash": bstr 32 }`. `records` MUST equal the finalized record's own `record_id` (the number of records before it in the segment), and `final_hash` its own `prev_hash` (the preceding record's `record_hash`). It MUST be the last record of its segment. The verifier checks all three (R9).
- **`log.sealed`** (new): the last record of a log, written when the writer closes the log for good. `payload` is an empty map. Nothing may follow it, in that segment or in a later one (`SealedLogExtended`). A writer refuses to append to a sealed log.
- **`log.continued`**: the first record of a log MAY carry `payload["previous_log"]` = `{ "log_id": bstr 16, "segment": uint, "record_id": uint, "record_hash": bstr 32, "key_id": bstr 32 }`, naming the final head of the log it follows (for example after a key rotation). Verifiers treat it as data. It links the two logs for a reader; it is not a trust path.
- **`policy`** ([ADR-0003](../adr/0003-policy-attestation-payload-convention.md)) is unchanged.
- **Commitments for content that may be withheld.** A payload value derived from content that may later be withheld, such as the hash of a page, MUST be a commitment `TH("ogentic-audit/v0.2/commit", nonce ‖ content)` with a fresh 32-byte random nonce per item. It MUST NOT be a plain hash: a plain SHA-256 of a short or templated page lets anyone confirm a guess. The nonce is recorded where it will not be released (for example in a separate record whose body is elided in releases), and disclosed only to a party entitled to the content, such as a court reviewing it in camera, who can then check the content against the commitment.

## 7. Chain invariants

For a log with segments `0..n`:

1. **Segment files.** A segment file is named exactly `audit-NNNN.cbor`, with four decimal digits. Indices run contiguously from `0000` with no gaps or duplicates. A gap is `SegmentDiscontinuity` at the first missing index. Any other entry is not a segment. A near-miss name such as `audit-1.cbor` or `AUDIT-0001.cbor` is a warning from `verify` (`NearMissSegmentName`) and an unattested file to `verify-release` (§11.4).
2. **Segment links.** Segment 0's `prev_final` is 32 zero bytes. Segment N ≥ 1's `prev_final` equals the `record_hash` of segment N−1's last record. Only the **last** segment may hold no records, because the writer creates a header before its first append. A record-less segment followed by another is `SegmentDiscontinuity` at the following segment. A header-only last segment is unsigned, and anyone can forge one from public data. It is reported as a warning (`UnsignedLastSegment`) and is not counted as an inspected segment.
3. **Record links.** Record 0 of every segment has `prev_hash = chain_start_N`. Every other record has `prev_hash` equal to the preceding record's `record_hash`.
4. **Signatures.** Every record's signature verifies strictly (§3.5) under the header public key in namespace `ogentic-audit/v0.2/record`, and that key is accepted for the record (§9.5).
5. **Fields.** Every envelope's `record_id`, `segment_index`, `key_id`, and `sig_alg` agree with its position and header. A present body hashes to `body_hash`.
6. **Rollover.** `segment.finalized` is the last record of its segment and its payload matches (§6.3). A segment that ends in `segment.finalized` has a successor. If it has none, that is a warning (`RolledOverWithoutSuccessor`: "segment N was rolled over, but segment N+1 is missing"), and the tail is not anchored.
7. **Sealing.** Nothing follows `log.sealed`.
8. **Time.** Timestamp rules are v0.1's.

Because each signature covers `prev_hash`, the signature on any record commits to the entire history before it. **The signature on the head record is a signed head**; a separate periodic signature would add nothing. A signed head is not an anchored one: every prefix of a log also ends in a signed head. Anchoring (§8.5) is what tells a verifier that nothing was cut.

Rollover follows v0.1: a `segment.finalized` record, `fsync`, then the next segment's header.

### 7.1 Writer obligations

- **Durability.** Append-only, with `F_FULLFSYNC`/`fsync` discipline and torn-tail recovery as in v0.1.
- **Reopening.** On reopen, the writer walks the hash links of the last segment from its `chain_start` and verifies the signature of its last complete record. Each signature covers `prev_hash`, so that one signature authenticates every earlier envelope in the segment, given SHA-256 collision resistance. A corrupted earlier record breaks a hash link. The writer refuses to resume if either check fails. This keeps reopening cheap for an embedding that opens the writer once per append; verifying every signature would cost seconds per call on a full segment.
- **No mixing.** A writer MUST refuse to append to a log whose format, algorithm, key, or `log_id` differs from its own (`WriterError::FormatMismatch`), or which ends in `log.sealed` (`WriterError::Sealed`).
- **Randomness.** `log_id` and every body `nonce` come from the OS CSPRNG.
- **Signing hygiene.**
  - Derive the public key from the private seed for every signature. Never sign with a separately stored public key: two signatures over one message under different public keys reveal the private key.
  - Verify every signature (§3.5) before writing it, so that a fault during signing cannot put out a faulty signature from which the key could be recovered.
  - Never expose the private key through any API. Signing happens behind a `Signer` handle (§13).
  - Never write the private key in OpenSSH private-key format, and never load it into `ssh-agent`. An agent signs in any namespace, for any host it is forwarded to.

## 8. Verifying a log

### 8.1 Inputs and mode

Inputs:

- the log directory;
- a trust context: pins, statements, revocations (§9). Any of them may be empty;
- optionally, checkpoints and witness co-signatures (§10);
- optionally, `--expect-log-id <32 hex>`: the log the caller means. A log with another `log_id` is the violation `LogIdMismatch@s0`.

The verifier reads segment 0's `version` **before** it loads any key. An HMAC key counts as supplied only when the caller passed it on the command line (`--key-source` or `--key-file`; in the Rust CLI, `ArgMatches::value_source` is `CommandLine`) or as an explicit library argument. A default, or an environment variable that happens to be set, never selects HMAC verification.

The **signed-only inputs** are `--public-key`, `--key-fingerprint`, `--trust`, `--statements`, `--revocations`, `--expect-log-id`, and a v2 checkpoint.

| Segment 0 version | Caller supplied | Result |
|---|---|---|
| `0x0002` | any signed-only input | signed verification (§8.2) |
| `0x0002` | nothing | signed verification; the best verdict is `SelfConsistent` (exit 4) |
| `0x0002` | an HMAC key | **argument error** (exit 3): "this is a signed log; pass the signer's public key or fingerprint". Never an HMAC verification |
| `0x0001` | any signed-only input | **error `HmacLog`** (exit 3): "this log is protected by a shared secret key (format 0x0001). It cannot be checked with a public key, and whoever holds its key could also have written it". Never `Verified`, and never an accusation of tampering |
| `0x0001` | an HMAC key, and no signed-only input | v0.1 verification, unchanged, except that a `Verified` result is labelled **shared-key**: the human output says "Verified with a shared key: anyone holding this key could have written this log", and the JSON report adds `"authentication": "shared-key"` |
| `0x0001` | nothing | argument error (exit 3): "this is an HMAC log; pass its key with --key-source or --key-file". The verifier never falls back to an implicit key source |
| higher than implemented | anything | argument error (exit 3): "this log uses format 0x000N; upgrade the verifier" (§4) |

No segment files: an error (`NoSegments`, exit 2), never a report.

These rules close a downgrade that would otherwise beat a correct pin. Someone holding a release could replace its signed log with an HMAC log made under a key of their choosing, and ship the instruction to verify it with that key in an environment variable. Under the rules above, that log never verifies implicitly, never verifies when the caller gave a pin, and when verified with an explicit key is labelled as checkable by anyone holding that key. Inside a release, an HMAC log in place of a signed one is the violation `FormatDowngrade` (§11.4 L2), because the signed attestation said otherwise.

### 8.2 Algorithm

```
segments = segment files (§7 invariant 1), in index order
final = 0^32;  trusted_sig = false;  count = 0
for (N, file) in segments:
    H = parse_header(file, expected_prev_final = final,
                     expected = segment 0's sig_alg, log_id, key_id, public_key)   # H1–H12
    if N == 0:
        if --expect-log-id given and H.log_id differs: → LogIdMismatch@s0
        if any pin was given and H.key_id is not trusted with the record scope (§9.5):
            → UntrustedSigner@s0, stop
    prev = chain_start(H)
    for (p, rec) in records(file):                                            # R1–R11
        prev = record_hash(rec);  count += 1
        if the signature verified and the key is accepted at this position (§9.5):
            trusted_sig = true
    final = prev        # a record-less segment must be the last one (§7)

check each supplied checkpoint and witness (§10.4)
anchored = is the last record anchored? (§8.5)

verdict = Violation       if any violation
        = Verified        if trusted_sig
        = SelfConsistent  otherwise   (no pin given, or no record)
```

`Verified` requires **at least one signature verified under a key the verifier trusts for that record**. A header-only log, or any log checked without a pin, can at best be `SelfConsistent`.

### 8.3 Checks, order, and report kinds

Checks run in this order. The first failure is the reported violation; forensic mode continues, as in v0.1. Locations use the record's **position** (`s<segment>r<position>`). Human output numbers records from 1 and adds the position: "record 3 (s0r2)". The evidence carries any value the record claims.

**Segment header** (location `s<N>`):

| # | Check | Kind | Evidence |
|---|-------|------|----------|
| H1 | file ≥ 12 bytes | `HeaderCorrupt` (`Truncated`) | message |
| H2 | `magic == "OGAU"` | `HeaderCorrupt` (`BadMagic`) | actual magic |
| H3 | `version == 0x0002` | `FormatDowngrade` if `0x0001` (a v0.1 segment in a v0.2 log); for segment 0, §8.1 applies first; otherwise `UnknownVersion` | actual, expected version |
| H4 | `sig_alg` implemented | `UnsupportedAlgorithm` | actual `sig_alg`, supported list |
| H5 | file ≥ `H` bytes | `HeaderCorrupt` (`Truncated`) | message |
| H6 | CRC32 over `[0, 92+P)` | `HeaderCorrupt` (`CrcMismatch`) | expected, actual CRC |
| H7 | `reserved == 0` | `HeaderCorrupt` (`ReservedBytesNonZero`) | actual bytes |
| H8 | `public_key` passes §3.5 rules 1–3 | `SignatureInvalid` (`weak_key`) | key |
| H9 | `key_id == SHA-256(key blob(public_key))` | `KeyIdMismatch` | header `key_id`, computed |
| H10 | N ≥ 1: `sig_alg`, `log_id`, `key_id`, `public_key` equal segment 0's | `AlgorithmMismatch` / `LogIdMismatch` / `KeyIdMismatch` | both values |
| H11 | `segment_index` equals the file-name index | `SegmentDiscontinuity` | expected, actual index |
| H12 | `prev_final` (zero for N = 0; else the previous segment's final `record_hash`) | `HeaderCorrupt` (`GenesisPrevFinalNonZero`) for N = 0; `SegmentDiscontinuity` for N ≥ 1 | expected, actual |

**Record** (location `s<N>r<p>`):

| # | Check | Kind | Evidence |
|---|-------|------|----------|
| R1 | `len_prefix` within the §3.8 limit; framing complete; `len_trailer == len_prefix` | `RecordCorrupt` (`TooLarge`, `TornTail`) | byte offset |
| R2 | signature verifies strictly (§3.5) over `signed_data(record ns, envelope_bytes)` | `SignatureInvalid` (`mismatch` / `reencoded`) | envelope offset and length, signature hex, `key_id` |
| R3 | a present body hashes to the envelope's `body_hash` | `SignatureInvalid` (`body_mismatch`) | expected, actual `body_hash` |
| R4 | envelope (and body, if present) is canonical CBOR with the §6 schema | `RecordCorrupt` (`DecodeError`) | decoder message |
| R5 | `key_id` field == header | `KeyIdMismatch` | both |
| R6 | `sig_alg` field == header | `AlgorithmMismatch` | both |
| R7 | `segment_index` == N, `record_id` == p, `prev_hash` == expected | `ChainBreak` | expected/actual `prev_hash`, expected/actual position, `is_segment_start` |
| R8 | the key is accepted for this record: not revoked (§9.4), not retired (§9.3) at this position | `RevokedKey` / `RetiredKey` | the statement's `issued_at`, the cut point if any |
| R9 | structural records: `segment.finalized` is last in its segment and its payload matches (§6.3); `log.sealed`, `segment.finalized` and `log.continued` are not elided | `RecordCorrupt` (`BadRollover`, `ElidedStructural`) | expected, actual |
| R10 | no record follows `log.sealed` | `SealedLogExtended` | position of the seal |
| R11 | timestamp rules (v0.1) | `TimestampRegression` / `TimestampInconsistency` | as v0.1 |

**Why signature before decode and before the chain (R2 first).** A flipped byte anywhere in a record's envelope or signature makes R2 fail **at that record**, and a flipped byte in its body makes R3 fail there. The report therefore names the altered record rather than a decode error or a chain break one record later. A record whose signature verifies but whose position or `prev_hash` is wrong is a genuine record in the wrong place: a deleted neighbour, a reordering, or a splice from another log by the same key. That is `ChainBreak`. The kinds separate "altered" from "moved or missing".

**What each attack reports.**

| Attack | Report |
|---|---|
| one byte changed in an envelope or a signature | `SignatureInvalid@sNrP` naming the record |
| one byte changed in a body | `SignatureInvalid@sNrP` (`body_mismatch`) |
| a body elided | not a violation: the record still verifies, and the report counts and lists it as elided |
| a signature re-encoded (`S + L`) | `SignatureInvalid@sNrP` (`reencoded`): signed content unchanged, signature bytes changed |
| record removed | `ChainBreak` at the removed record's position |
| records swapped | `ChainBreak` at the first swapped position |
| middle segment deleted | `SegmentDiscontinuity` |
| log re-signed with another key | `UntrustedSigner@s0` (with a pin) |
| v0.1 segment substituted | `FormatDowngrade@sN` |
| whole log replaced by an HMAC log | error `HmacLog` (exit 3) under a pin; `FormatDowngrade` in a release |
| another log by the same key passed off as this one | `LogIdMismatch@s0` with `--expect-log-id`; `CheckpointForDifferentLog` against a checkpoint (§10.4) |
| tail truncated, or trailing segments deleted | `Verified`, but **"tail not anchored"** (§8.5). With a checkpoint, `CheckpointTruncated` |
| a header-only segment appended | warning `UnsignedLastSegment`; not counted |
| log rewritten by the key holder | not detectable without a checkpoint (§10); with one, `CheckpointMismatch` |

### 8.4 Errors (not violations)

Operator mistakes never read as accusations. They are errors, as in v0.1:

- exit 2: no segments (`NoSegments`); an unreadable directory;
- exit 3, the caller's inputs:
  - a malformed pin, fingerprint (§3.7), trust file (§9.1), or statement or revocation file passed by the operator;
  - a pinned key that fails §3.5 rules 1–3;
  - an HMAC key for a signed log; a signed-only input for an HMAC log (`HmacLog`); an HMAC log with no explicit key;
  - a log format newer than the verifier;
  - a v1 (HMAC) checkpoint for a v0.2 log, or a v2 checkpoint for a v0.1 log;
  - a checkpoint for a different signer (`CheckpointForDifferentSigner`, §10.4);
  - a checkpoint or witness signature that does not verify, or is not made by a key trusted for that namespace (`CheckpointSignatureInvalid`, `CheckpointSignerUntrusted`);
  - a revocation passed by the operator that does not verify, or whose signer has no authority over the key it revokes (§9.4). A revocation the verifier cannot honour stops the run. It is never skipped.

### 8.5 Anchoring, verdicts, and exit codes

Every prefix of a signed log is itself a validly signed log, so a verifier must say whether the end it reached is the real end. The last record is **anchored** when any of these holds:

- it is a `log.sealed` record;
- a trusted checkpoint (§10.4) or witness co-signature names it;
- in a release, it is the attested head (§11.4 L3).

Otherwise the tail is **not anchored**. Records or whole segments after the last record could have been removed, and nothing in hand would show it. The verdict can still be `Verified`, because a log that is still being written is never anchored, but the report says so: the human output reads "Verified through record 1,207 (s1r206) · tail not anchored: later records may have been removed", and the JSON report has `"head_anchored": false`.

| Verdict | Meaning | CLI exit | JSON `status` |
|---------|---------|----------|---------------|
| `Verified` | No violation, and at least one signature verified under a key trusted for it | 0 | `"ok"` |
| `SelfConsistent` | No violation, but either no key was supplied (reason `not_pinned`) or the log has no records to check a key against (reason `no_signed_records`). **Not a verification.** The two reasons print different messages (§11.6) | **4** | `"unpinned"` |
| `Violation` | At least one violation | 1 | `"tampered"` |

Exit code 4 is new and is produced only for v0.2 inputs. Scripts that treat any non-zero exit as failure fail closed on `SelfConsistent`. The full exit-code table is in the CLI's `--help` (§13).

## 9. Trust: pins, scopes, rotation, revocation

### 9.1 Pins and scopes

A pin is a public key or fingerprint the verifier obtained **outside** the artefact under verification: from the signer's website, a letter, a phone call, a court filing. Each pin has a **principal** (who it belongs to) and a **scope** (the namespaces in which its signatures are accepted).

Sources, accepted by the CLI and both libraries:

- `--public-key <file|line>`: a public key in any §3.7 format. Default scope; a principal of its own;
- `--key-fingerprint <fp>` (repeatable): a fingerprint in a §3.7 form. Default scope; each one a principal of its own. The public key bytes then come from the artefact (segment header, SSHSIG blob, or transition statement) and are accepted only if they hash to the pinned fingerprint;
- `--trust <file>`: a **trust file**, in the OpenSSH `allowed_signers` format restricted to lines of the form

  ```
  <principal> [namespaces="<namespace>,<namespace>,…"] ssh-ed25519 <base64> [comment]
  ```

  `principal` is a single name of letters, digits, and `. _ @ -`. The only option allowed is `namespaces`, listing exact namespaces from §3.3, with no wildcards. Any other option (`cert-authority`, `valid-after`, `valid-before`, or an unknown one) is an argument error: we do not implement them, and we never ignore one silently. `#` comments and blank lines are allowed. `ssh-keygen -Y verify` honours the same `namespaces` option, so the file also drives the stock-tools path (§11.7).

| Scope | Namespaces | Typical use |
|-------|-----------|-------------|
| **default** (a line with no options, `--public-key`, `--key-fingerprint`) | record, checkpoint, release, key-transition, key-revocation | the party that writes logs and releases |
| witness | `ogentic-audit/v0.2/witness` | an auditor or other party co-signing checkpoints |
| revocation-only | `ogentic-audit/v0.2/key-revocation` | an offline backup key that can only revoke |

Any combination may be listed. Every signature is accepted only if its namespace is in the scope of the key that made it. A record, checkpoint, or attestation signed by a trusted key outside its scope is `UntrustedSigner` (reason `out_of_scope`) or, for an operator-supplied checkpoint, an argument error. A witness key can therefore never sign a log or a release that verifies, mint a transition, or revoke anything. Reports print the principal's name next to every key.

A public key embedded in a segment header, in an SSHSIG blob, in `ogentic-audit-signer.pub`, or printed in a release's instructions is **informational only**. It is never a pin. A verifier with no pin MUST NOT report `Verified` (§8.5).

### 9.2 Statements

Key transitions and revocations are canonical-JSON files with detached SSHSIG signatures (`<name>.json` + `<name>.json.sig`, and for a transition also `<name>.json.accept.sig`). They are self-authenticating, so they may travel inside an untrusted bundle (directory `ogentic-audit-keys/`) or be passed with `--statements <dir>`. A transition can only extend trust from a key the verifier already trusts. A revocation can only reduce trust. An unparseable or unverifiable statement found in a bundle is ignored with a warning; it never adds trust. One passed by the operator is an argument error (exit 3).

**Who signed a statement.** As for every detached object (§3.3), the SSHSIG key's fingerprint MUST equal the signer field the statement names: `old_key_id` for a transition, `new_key_id` for its acceptance, `revoker_key_id` for a revocation. The verifier verifies under the trusted key it looks up by that field, never under a key merely because it appears in the blob. A statement signed by any other key, including one that claims to come from a pinned key, is rejected.

### 9.3 Key transition (rotation)

```json
{"final_heads":[{"log_id":"<32 hex>","record_count":42,"record_hash":"<64 hex>","record_id":41,"segment":0}],"final_releases":["<64 hex>"],"format":"ogentic-audit-key-transition/v1","issued_at":"2027-01-15T09:00:00.000Z","new_key_id":"<64 hex>","new_public_key":"ssh-ed25519 AAAA…","old_key_id":"<64 hex>","reason":"scheduled"}
```

(Canonical form: sorted keys, no whitespace. `reason` is optional free text, subject to the string rules of §11.2.)

| Field | Rule |
|-------|------|
| `old_key_id` | the key being retired |
| `new_key_id`, `new_public_key` | the successor. `new_key_id` MUST equal `SHA-256(key blob(new_public_key))`, and the key MUST pass §3.5 rules 1–3. Its algorithm (its key type) MUST NOT be weaker than the old key's (§3.2) |
| `final_heads` | the head of every log the old key signed, as `(log_id, segment, record_id, record_count, record_hash)`. Each SHOULD be a `log.sealed` record |
| `final_releases` | SHA-256 of the bytes of every release attestation the old key signed |
| `issued_at` | the signer's clock |

**Two signatures, both required.** The old key signs the file in namespace `ogentic-audit/v0.2/key-transition` (`<name>.json.sig`). The new key signs the **same bytes** in namespace `ogentic-audit/v0.2/key-transition-accept` (`<name>.json.accept.sig`). The acceptance proves the new key's holder agreed to become the successor. Without it, one key could claim another's key as its successor and make that key's genuine releases verify under its own pin, as if it had made them. A transition is **verified** when both signatures verify, under keys equal to `old_key_id` and `new_key_id` respectively, and every rule in the table holds.

**Effects** of a verified transition whose old key is trusted with `key-transition` in scope (§9.5):

1. **The new key becomes trusted**, with the old key's principal and scope, and `trust_path(new) = trust_path(old) + [new]`. It never gets a wider scope than the old key had.
2. **The old key is retired.** From then on, its signatures are accepted only on:
   - records of a log in `final_heads`, at or before that head (whose `record_hash` MUST be present at that position, otherwise `CheckpointMismatch`);
   - checkpoints of such a log at or before its final head;
   - release attestations whose SHA-256 is in `final_releases`;
   - the transition itself, and revocations.

   Anything else signed by the old key is the violation **`RetiredKey`**: a new log, a later record, a later release. A copy of the old key stolen before it was destroyed can therefore not produce anything that verifies for a verifier who has the transition. That verifier always has it, because the new key's artefacts verify under the old pin only through the transition.
3. **One transition per key.** Two different verified transitions from the same old key are the violation **`TransitionEquivocation`** (item `key:<old fingerprint>`). Each is self-contained evidence that the key's holder signed two successions. The verifier then follows **neither**: their successors are trusted only if pinned directly or listed by an authority revocation's `trusted_successors` (§9.4).

**Rotation** is: seal the current logs (`log.sealed`); generate the new key; sign the transition with the old key and accept it with the new one; open **new** logs with the new key; ship the transition in `ogentic-audit-keys/` with every later release and publish it next to the pins; then destroy the old private key ([key-rotation.md](../security/key-rotation.md#signed-mode-format-0x0002)). Logs never change key mid-stream (§4). A verifier pinned to the root key reaches any later key through the chain of transitions, and transition chains of any length are followed.

### 9.4 Revocation

```json
{"format":"ogentic-audit-key-revocation/v1","issued_at":"…","reason":"compromised","revoked_key_id":"<64 hex>","revoker_key_id":"<64 hex>","trusted_heads":[{"log_id":"<32 hex>","record_count":42,"record_hash":"<64 hex>","record_id":41,"segment":0}],"trusted_releases":["<64 hex>"],"trusted_successors":["<64 hex>"]}
```

Signed in namespace `ogentic-audit/v0.2/key-revocation` by `revoker_key_id`. The three `trusted_*` lists are the **cut points**: what the revoked key signed that is still vouched for. `trusted_releases` holds SHA-256 values of attestation bytes, so a revocation need not break every release the key made before the compromise.

**Authority.** A revocation of key K is honoured only if `revoker_key_id` is:

1. **K itself** (a self-revocation). It marks K revoked. Its cut-point lists are **ignored**; writers emit them empty. A key thief can always revoke the stolen key, so a self-revocation can never decide what survives; or
2. **a directly pinned key** (not one reached through a transition) that has `key-revocation` in its scope and the same principal as K. Since a transition gives the new key the old key's principal, this includes the pin K's trust path starts from. This is an **authority revocation**.

Any other signer, including a key reached only through transitions or a co-pinned key of another principal, has no authority over K. Its revocation is ignored with a warning when found in a bundle, and is an argument error when passed by the operator.

**Combining revocations.** The result depends only on the set of revocations, never on their order or their `issued_at`:

- K is revoked if **any** honoured revocation of K exists.
- K's cut points come **only** from authority revocations. With several, each list is the **intersection** of theirs. With none (K is only self-revoked), the cut points are empty.

A self-revoked key's history therefore cannot be verified until an authority revocation issues cut points for it. That is deliberate: it fails closed, and only the authority decides what survives a compromise.

**Effect.** After a revocation of K, a signature by K is accepted only:

- on a record of a log in `trusted_heads` (matched by `log_id`), at or before that head, with that head's `record_hash` present at that position (otherwise `CheckpointMismatch` against the head), and on a checkpoint of such a log at or before that head;
- on a release attestation whose SHA-256 is in `trusted_releases`;
- on a transition to a key in `trusted_successors`.

Everything else signed by K is `RevokedKey`: later records, other logs, checkpoints, attestations. A key that is both retired and revoked must pass both rules. A revoked signer re-issues release attestations under its new key; the released files are unchanged.

**Distribution.** A verifier cannot learn of a revocation it is not given. Revocations MUST be published through the same out-of-band channel as the pins, and verifiers pass them in (`--revocations <file>`, repeatable). A bundle may also carry them, but omitting one from a bundle is exactly what an attacker would do. Each revocation is published together with an **OpenSSH key revocation list** (`ssh-keygen -k`) naming every revoked key, for the stock-tools path (§11.7). A KRL is all or nothing: under it, stock tools reject every signature by the key, including those the cut points would keep. That path therefore fails closed.

### 9.5 Trust evaluation

A key can be trusted under one or more **entries** `(principal, scope, trust_path, pinned)`. Pins create entries with `pinned = true`.

```
entries = pins
repeat until no entry is added:
    for each verified transition T (old → new):
        for each entry E of T.old with "key-transition" in E.scope:
            if T.old has a TransitionEquivocation: skip
            if T.old is revoked and T.new ∉ cut(T.old).trusted_successors: skip
            add (E.principal, E.scope, E.trust_path + [T.new], pinned = false) to T.new
```

Each `(key, principal)` pair is added at most once, so the loop ends after at most one pass per statement. A revocation of K is honoured if it is honoured under **any** of K's entries (§9.4), and a revoked key stays revoked under all of them. Revocation authority comes only from pinned entries, which transitions never create, so the result does not depend on the order statements are processed in.

A signature by key K in namespace `ns` at a position is **accepted** iff K has an entry whose scope contains `ns`, and K's retirement (§9.3) and revocation (§9.4) rules allow that object. The report records each signer's principal and `trust_path` (pinned key first).

**Pin the newest key you can obtain out of band.** Retirement stops a stolen *old* key from signing new artefacts, but until a revocation reaches the verifier, a compromised *current* key can still mint a transition. A pin of the newest key limits that to keys that came after it.

## 10. Checkpoints and witnesses

### 10.1 Checkpoint format

```json
{"alg":"ed25519","format":"ogentic-audit-checkpoint/v2","head_ts_wall":"2026-10-03T11:59:58.120Z","key_id":"<64 hex>","log_id":"<32 hex>","observed_at":"2026-10-03T12:00:00.000Z","record_count":42,"record_hash":"<64 hex>","record_id":41,"segment":0}
```

| Field | Meaning |
|-------|---------|
| `alg`, `key_id` | the log's signer and its algorithm, as in the log's header |
| `log_id` | the log's random id from its header (§4), 32 hex digits |
| `segment`, `record_id` | position of the head (`record_id` ≤ 2^53−1) |
| `record_count` | records from s0r0 through the head, inclusive, across segments (≥ 1: a log with no records has no head to checkpoint) |
| `record_hash` | the head's `record_hash` |
| `head_ts_wall` | the head record's `ts_wall` (copied; signer's clock) |
| `observed_at` | when the checkpoint was made (the maker's clock) |

The file is canonical JSON (§3.6). It is either:

- **signed by the log's signer**: a detached signature `<file>.sig` in namespace `ogentic-audit/v0.2/checkpoint`, by `key_id`. This is the signer's own non-repudiable statement "my log had this head". Anyone holding it can later prove truncation or rewriting against the signer; or
- **unsigned**: the verifier's own observation, worth what the verifier's own record-keeping is worth.

v1 checkpoints (`ogentic-audit-checkpoint/v1`, HMAC) remain the format for v0.1 logs. The formats are never interchangeable (§8.4).

### 10.2 Witness co-signatures

A witness (an auditor, a requester, a transparency service) attests that **it** observed a checkpoint, at **its** time, with its own key and its own envelope:

```json
{"checkpoint_sha256":"<64 hex>","format":"ogentic-audit-witness/v1","observed_at":"2026-10-03T12:05:00.000Z","witness_key_id":"<64 hex>"}
```

`checkpoint_sha256` is the SHA-256 of the checkpoint file's bytes. The co-signature is signed in namespace `ogentic-audit/v0.2/witness` by `witness_key_id`, whose pin must have the witness scope (§9.1). `observed_at` is the witness's clock, not the signer's. Witness files are passed with `--witness <file>` (repeatable) or carried in a bundle's `ogentic-audit-witness/` directory. A witness never signs in the checkpoint namespace, so a witness can never be mistaken for the log's signer.

### 10.3 Making them

`ogentic-audit checkpoint <log>` needs no key: anyone holding a log can record an unsigned v2 observation after verifying it. With `--sign <signer>`, the log's key signs it. `ogentic-audit witness <checkpoint> --sign <witness key>` writes a co-signature. The signer SHOULD hand signed checkpoints to parties with different interests (the requester, an auditor, a transparency log) at meaningful moments: release, session close, rotation.

### 10.4 Verifying against them

After the walk (§8.2), for each checkpoint:

1. A `.sig` is present → its key MUST equal `key_id` and be accepted for the checkpoint namespace at that position (§9.5), and the signature MUST verify strictly. Otherwise, **error** `CheckpointSignatureInvalid` / `CheckpointSignerUntrusted` (exit 3). A checkpoint that cannot be authenticated is not evidence about the log, so it never produces a violation against the log.
2. Each witness co-signature for it MUST verify under a key with the witness scope, and its `checkpoint_sha256` MUST match. Otherwise, the same errors. The report lists each witness by principal and `observed_at`.
3. `key_id` or `alg` differs from the log's header → error `CheckpointForDifferentSigner` (exit 3). This is another signer's checkpoint, an operator mistake.
4. `log_id` differs from the log's header → violation **`CheckpointForDifferentLog`** (location `s0`). The checkpoint is by this log's own signer, about a different log. Either the wrong log was supplied, or the log the checkpoint describes was replaced by another of the signer's logs. The report says both, and does not decide between them.
5. The position does not exist → **`CheckpointTruncated`**: history the checkpoint saw is gone.
6. The position exists but its `record_hash`, or `record_count` at that position, differs → **`CheckpointMismatch`**: history rewritten.
7. A checkpoint that passes and names the last record anchors it (§8.5).

### 10.5 Equivocation evidence

Two checkpoints signed by the same key for the same `(log_id, segment, record_id)` but with a different `record_hash` or `record_count` are a self-contained, verifiable proof that the signer published two histories of one log. `ogentic-audit checkpoint compare <a> <b>` checks this. It is the strongest answer to a signer who rewrites their own log, and it needs only that someone kept an earlier signed checkpoint.

Because `log_id` is random and fixed at creation (§4), a rewrite that keeps the log's identity is caught here. A rewrite under a new `log_id` is a different log: the earlier signed checkpoint then remains signed evidence that a log with the old id existed and had that head, which the signer must account for. Two transitions from one key (§9.3) are the corresponding proof for successions.

## 11. Release attestation (the offline verifier bundle)

### 11.1 Bundle layout

```
<release>/
  …released files…                     (any depth)
  HOW-TO-VERIFY.txt                    attested instructions (§11.9)
  <log dir>/audit-NNNN.cbor            one or more v0.2 logs, as released (§11.3)
  ogentic-audit-verifier/              optional: verifier binaries and wheels, ATTESTED (§11.8)
  ogentic-audit-release.json           the attestation (canonical JSON)
  ogentic-audit-release.json.sig       SSHSIG, namespace ogentic-audit/v0.2/release
  ogentic-audit-signer.pub             OpenSSH line: informational, never a pin
  ogentic-audit-keys/                  optional: transitions and revocations
  ogentic-audit-witness/               optional: witness co-signatures
```

The **reserved bundle entries** are the last five names. They are not attested, and are self-authenticating or informational. Everything else in the bundle is either attested or reported (§11.4 U1). In particular, files under `ogentic-audit-verifier/` MUST be listed in `files[]` with role `verifier`, so that anyone checking the attestation with stock tools (§11.7) has also checked the verifier before running it.

### 11.2 Format

```json
{
  "alg": "ed25519",
  "created_at": "2026-10-03T12:00:00.000Z",
  "files": [
    {"parts": [{"length": 14, "name": "header", "offset": 0, "sha256": "<64 hex>"},
               {"length": 4, "name": "row 1", "offset": 14, "sha256": "<64 hex>"}],
     "path": "Decisions.csv", "role": "index", "sha256": "<64 hex>", "size": 18},
    {"path": "pages/0001.pdf", "role": "page", "sha256": "<64 hex>", "size": 10}
  ],
  "format": "ogentic-audit-release/v1",
  "key_id": "<64 hex>",
  "logs": [
    {"checkpoint": {"alg": "ed25519", "head_ts_wall": "…", "key_id": "<64 hex>", "log_id": "<32 hex>",
                    "record_count": 42, "record_hash": "<64 hex>", "record_id": 41, "segment": 0},
     "path": "Audit log"}
  ],
  "release_id": "<text>"
}
```

(Pretty-printed for reading; the file itself is canonical and single-line, §3.6.)

| Field | Rule |
|-------|------|
| `format` | `"ogentic-audit-release/v1"` |
| `alg`, `key_id` | the attestation signer. `key_id` MUST equal the SSHSIG key's fingerprint, and `alg` its key type |
| `release_id` | caller-defined text, 1–256 characters |
| `created_at` | RFC 3339 UTC, millisecond precision, `Z` (the signer's clock) |
| `files[]` | every released file; sorted by `path` bytes; `path` unique |
| `files[].size`, `.sha256` | byte length and SHA-256 of the file |
| `files[].role` | optional caller-defined text (for example `page`, `document`, `index`, `instructions`, `verifier`). Opaque to the verifier |
| `files[].parts[]` | optional byte ranges naming items inside a file, such as the rows of an index: sorted by `offset`, non-overlapping, `length ≥ 1`, inside `size`, `name` unique within the file |
| `logs[]` | every audit log in the bundle, sorted by `path`. `checkpoint` is the §10.1 object without `format` and `observed_at`. Its `key_id` and `alg` MUST equal the log header's |

**Strings.** In `path`, `parts[].name`, `role`, `release_id`, and `reason` (§9.3), these code points MUST NOT occur: U+0000–U+001F, U+007F–U+009F, U+2028–U+2029, U+200E–U+200F, U+202A–U+202E, U+2066–U+2069. They would let a name rewrite the line a verifier prints (escape sequences, carriage returns), reorder it (bidirectional overrides), or inject a line into the output of `shasum -c` (a newline followed by a hash and another file name). A document breaking this rule is `AttestationMalformed`.

**Paths.** Relative, `/`-separated, UTF-8 in Unicode NFC. No empty, `.`, or `..` components; no leading `/`; no `\`. Not a reserved bundle entry or inside one. Not a segment file of a listed log (other files inside a log directory may be listed). No two paths equal after Unicode default case folding, because they would collide on a case-insensitive filesystem.

**Naming the altered item.** A part is a contiguous byte range, so it names items laid out contiguously, such as the rows of a CSV index. A page inside a PDF is not contiguous: its bytes are spread over objects, and an incremental save appends at the end of the file. **A page is named by giving it its own file** (a single-page PDF or TIFF per page, with role `page`). A multi-page file is named only as a whole: the report says the file changed and that the changed page cannot be identified inside it.

**The page and decision index.** The attestation itself is the signed index of every released page's hash: each page file's `sha256` is in `files[]`. The per-item decision index (one row per page, with its decision and, for a withheld page, the exemption applied) is a released file with one part per row, so a changed row is named. Rows refer to released pages by their attested path, not by a hash of their own. A withheld page appears only as its row and as the commitment recorded in the audit log (§6.3), never as a plain hash.

**What goes in (normative).** Everything in a release is published in the clear, including every record body in its logs. Therefore:

- `files[]` lists only released files. Paths, part names, roles, and `release_id` MUST NOT contain withheld information;
- every record of a bundled log whose body carries withheld information MUST be elided (§5). A record's `event` name is always visible and carries no content (§6.1);
- values derived from withheld content are commitments (§6.3), whose nonces are not in the bundle.

The verifier cannot know what was withheld, so these are obligations on the release builder (§11.3), and a golden vector shows a release whose log has elided records verifying (§16).

### 11.3 Building and signing

The release builder (`AttestationBuilder`, §13):

1. verifies each log it includes, under the signer's own key, and refuses a log that does not verify;
2. copies each log **through the attested head and no further**, so no torn or unattested tail travels with it. It attests a log only at a `log.sealed` record or at a head the caller names explicitly;
3. elides the bodies of the records the caller marks as withheld, and refuses to elide a structural record;
4. hashes every released file, writes the attestation, `ogentic-audit-signer.pub`, `HOW-TO-VERIFY.txt` (§11.9), and the key statements and witness co-signatures it is given, then signs.

`signature = SSHSIG(namespace "ogentic-audit/v0.2/release", message = the attestation file bytes)`, by `key_id`. The signer is normally the log signer. A `logs[].checkpoint.key_id` MAY differ (for example a log written before a rotation), and every such key must be accepted for that log when verified.

### 11.4 `verify-release` algorithm

```
ogentic-audit verify-release <dir> (--public-key K | --key-fingerprint F | --trust FILE)
                             [--revocations FILE]… [--statements DIR]… [--witness FILE]…
                             [--expect-release-id ID] [--allow-unattested] [--format json]
```

Unlike a log, a release's items are independent, so the verifier checks **every** item and reports **all** violations, grouped (§11.6). A failure at A1–A6 ends the run, because comparing files against an attestation that is not authenticated proves nothing. With no pin at all, A3 is skipped and the run continues to a best verdict of `SelfConsistent`.

| # | Step | Failure → kind | Item |
|---|------|----------------|------|
| A1 | attestation file present | `AttestationMissing` | `attestation` |
| A2 | `.sig` present and parses strictly (§3.3) | `SignatureInvalid` (`missing`, `malformed`, `namespace`, `hash_alg`, `key_type`) | `attestation` |
| A3 | SSHSIG key trusted with the release scope, and accepted under retirement and revocation (§9.5) | `UntrustedSigner` (`not_trusted`, `out_of_scope`) / `RetiredKey` / `RevokedKey` | `attestation` |
| A4 | signature verifies strictly over the file bytes | `SignatureInvalid` (`mismatch`, `reencoded`, `weak_key`) | `attestation` |
| A5 | size limits (§3.8), canonical JSON, integer types, schema, string and path rules, `key_id` and `alg` match the SSHSIG key | `AttestationMalformed` (`KeyIdMismatch` for the key) | `attestation` |
| A6 | `release_id` equals `--expect-release-id`, when given | `ReleaseIdMismatch` | `attestation` |
| F1 | each `files[]` entry exists (§11.5) | `FileMissing` | `file:<path>` |
| F2 | it is a regular file, reached without following a symlink or reparse point, and its name is not ambiguous | `FileAltered` (`not_regular_file`, `ambiguous_name`) | `file:<path>` |
| F3 | `size` and `sha256` match. On mismatch, the reason is `size` if the length differs; otherwise `part`, naming the first declared part whose hash differs; otherwise `outside_parts` (every part matches) or `content` (no parts declared) | `FileAltered` | `file:<path>` or `file:<path>#<part>` |
| L1 | each `logs[]` directory exists | `FileMissing` | `log:<path>` |
| L2 | §8 verification of that log under the same trust context. An HMAC (`0x0001`) log here is `FormatDowngrade`, because the signed attestation names a signed log | any §8.3 kind | `log:<path>/s<N>r<P>` |
| L3 | the log contains the attested checkpoint: header `key_id` and `alg` equal the checkpoint's, `log_id` equal (otherwise `CheckpointMismatch`, because the attestation is evidence, not operator input), then §10.4 steps 5–6. The attested head anchors the log through that head | `CheckpointTruncated` / `CheckpointMismatch` | `log:<path>/s<N>r<P>` |
| L4 | records after the attested head | counted, not a failure. A torn tail after the head is a warning (`TornTailAfterHead`) | `log:<path>` |
| U1 | files not covered: not listed, not a segment file of a listed log, not a reserved bundle entry, and not on the ignore list below | `UnattestedFile`; with `--allow-unattested`, a warning | `file:<path>` |

**Unattested files fail by default.** A file someone planted in a bundle must not pass a script or the headline verdict. Only these names, at any depth, are ignored, because operating systems create them when a folder is browsed or copied: `.DS_Store`, `Thumbs.db`, `desktop.ini`, files beginning `._`, and the directories `__MACOSX/`, `.Spotlight-V100/`, `.Trashes/`. The report lists ignored entries by name. `--allow-unattested` turns `UnattestedFile` into a warning; the human report still lists every such file under "Not covered by the signature".

### 11.5 Name lookup

The verifier enumerates the release directory once, without following symlinks, Windows reparse points, or junctions, and maps each entry's NFC-normalized relative path to the entry. Attested paths are looked up by NFC equality, so a bundle that passed through a filesystem that stores names decomposed (NFD) still verifies. Two entries whose paths are equal after NFC normalization, or after Unicode default case folding, make that path ambiguous: `FileAltered` (`ambiguous_name`). It fails closed.

### 11.6 Reports and human output

**JSON** (`--format json`), `format: "ogentic-audit-release-report/v1"`:

| Member | Content |
|--------|---------|
| `verdict`, `status` | as §8.5 |
| `release_id` | from the attestation, escaped per §11.2 rules on output |
| `signer` | `{principal, alg, key_id_hex, fingerprint_grouped, fingerprint_openssh, trusted, trust_path, reason}` with `reason` one of `pinned`, `transition`, `not_pinned` |
| `files` | `{attested, verified, unattested: [path…], ignored: [path…]}` |
| `logs` | one §14 report per log, with `path`, `head_anchored`, `records_after_head`, `elided_records` |
| `violations` | `[{item, kind, reason, evidence}…]` in §11.4 order; `item` as in the table |
| `warnings` | `[{item, kind, message}…]` |

The schema is published with the implementation as `docs/spec/release-report.md`, alongside the `violation-report.md` v2 update (§14).

**Human output** goes entirely to standard output, so `> report.txt` keeps all of it; standard error carries only errors that prevent a report. It prints every violation, not only the first, grouped under **Altered**, **Missing**, and **Not covered by the signature**. Fingerprints are printed in full, in grouped hex, on a line of their own; there is no short form (§3.7). Every name taken from the bundle is shown with control, non-printing, and bidirectional characters escaped as `\u{XXXX}`. Where the console is not UTF-8 (for example a legacy Windows console), the marks `✓ ✗ !` become `[OK] [FAILED] [!]`. "Pinned" is not used; the output says "the key you supplied".

```
✓ Verified: release "2026-0147", 14 files, 1 audit log (2 segments, 1,207 records, 31 with withheld content)
  Signed by release-signer, the key you supplied:
    6db5 e9b8 a1ba ce1c dd9a 7c6a db9e 9396 acc5 0734 65d9 fe8e 3a0e f6d9 c60d 6d4f
  0 files not covered by the signature.

✗ Verification failed: 3 problems
  Altered
    "Decisions.csv", item "row 1" (bytes 15–18)
    "pages/0007.pdf": the content changed
  Missing
    "pages/0012.pdf"
  Not covered by the signature
    "extra.pdf"

  The files match the signature, but without the signer's key anyone could have made that signature.
  This release says it was signed by
    6db5 e9b8 a1ba ce1c dd9a 7c6a db9e 9396 acc5 0734 65d9 fe8e 3a0e f6d9 c60d 6d4f
  Do not take that number from the release itself. Get the signer's fingerprint from the signer
  directly (their website, a letter, a phone call), then run:
    ogentic-audit verify-release <folder> --key-fingerprint "<the fingerprint you were given>"
```

A file without parts that changed reads "the content changed". `outside_parts` reads "changed outside any named item (for example, data added at the end)". A file with role `page` or `document` that has no parts adds nothing more; the report never claims to name a page inside a multi-page file. Byte ranges in human output are 1-based and inclusive; JSON keeps 0-based `offset` and `length`.

### 11.7 Checking a release with stock tools only

The signature and the released files can be checked with no `ogentic-audit` software at all, using OpenSSH ≥ 8.1, `shasum` (or `sha256sum`), and `python3` (or `jq`). That is an implementation independent of ours. Run it **first**: it also checks the verifier binaries in the bundle (§11.8) before anyone runs them.

```sh
# 1. The key in the bundle is the key you were given. Compare by machine, not by eye.
#    FP is the fingerprint you obtained from the signer, in any grouping.
FP='6db5 e9b8 a1ba ce1c dd9a 7c6a db9e 9396 acc5 0734 65d9 fe8e 3a0e f6d9 c60d 6d4f'
HAVE=$(awk '{print $2}' ogentic-audit-signer.pub | base64 -d | shasum -a 256 | cut -c1-64)
WANT=$(printf '%s' "$FP" | tr -d ' :-' | tr 'A-F' 'a-f')
[ "$HAVE" = "$WANT" ] && echo "key matches" || echo "KEY DOES NOT MATCH: stop"
#    (Older macOS: base64 -D. Then confirm $WANT is not listed in Appendix A, a key
#    under which anyone can sign.)

# 2. A trust line for that key, valid only for release signatures.
echo "release-signer namespaces=\"ogentic-audit/v0.2/release\" $(cut -d' ' -f1,2 ogentic-audit-signer.pub)" > allowed_signers

# 3. The attestation is signed by that key, for this purpose. If the signer has published
#    a revocation list, add: -r revoked.krl
ssh-keygen -Y verify -f allowed_signers -I release-signer \
  -n ogentic-audit/v0.2/release \
  -s ogentic-audit-release.json.sig < ogentic-audit-release.json

# 4. Every released file matches; an altered file prints FAILED with its name.
python3 -c '
import json
def no_dupes(pairs):
    keys = [k for k, _ in pairs]
    if len(keys) != len(set(keys)): raise SystemExit("duplicate key: stop")
    return dict(pairs)
a = json.load(open("ogentic-audit-release.json", encoding="utf-8"), object_pairs_hook=no_dupes)
for f in a["files"]: print(f["sha256"] + "  " + f["path"])' | shasum -a 256 -c
```

With `jq` instead of Python, step 4 is `jq -r '.files[] | "\(.sha256)  \(.path)"' ogentic-audit-release.json | shasum -a 256 -c`. `jq` keeps the last of two duplicate keys and does not reject them; our verifier rejects a document with duplicates (§3.6), so the Python form is preferred.

On Windows (PowerShell, with the OpenSSH client that ships with Windows 10 and later), steps 1 and 4 are:

```powershell
$b = [Convert]::FromBase64String((Get-Content ogentic-audit-signer.pub).Split(' ')[1])
(Get-FileHash -Algorithm SHA256 -InputStream ([IO.MemoryStream]::new($b))).Hash   # compare with the fingerprint
$a = Get-Content -Raw -Encoding UTF8 ogentic-audit-release.json | ConvertFrom-Json
foreach ($f in $a.files) {
  $h = (Get-FileHash -Algorithm SHA256 -LiteralPath $f.path).Hash.ToLower()
  if ($h -eq $f.sha256) { "OK      $($f.path)" } else { "FAILED  $($f.path)" }
}
```

The POSIX path was exercised end to end against a hand-built attestation (RFC 8032 key, non-ASCII file names, one byte appended to one file: `ssh-keygen` returns 0 for the original, `shasum` prints `FAILED` for the altered file), and the step 1 command was checked against K1 (§16). The `namespaces=` option and `-r` revocation lists were checked with OpenSSH 10.3. The PowerShell form is checked in CI on Windows before it ships in instructions.

**What the stock path does not do.** It does not check `parts`, the audit-log chain, or checkpoints; for those, use an `ogentic-audit` verifier or an independent implementation of §8. It follows **no transitions**: pin the key that signed this attestation, not a root key. It applies **no cut points**: a revocation list rejects every signature by a revoked key (§9.4). It does not apply rule 2 of §3.5 by itself; step 1's Appendix A check stands in for it. And `ssh-keygen` accepts a re-encoded signature (`S + L`) that `ogentic-audit` reports as `reencoded`; the two results then differ for that stated reason.

### 11.8 Obtaining the verifier

A verifier taken from the bundle without checking it vouches for itself: anyone who can alter the bundle can replace it with a program that always prints "Verified". So:

1. **Get the verifier independently** where possible: the public GitHub releases of this repository, crates.io (`cargo install ogentic-audit --locked`), or PyPI (`pip install ogentic-audit`). Instructions state the minimum version: **0.4.0** (§4).
2. **Check it offline.** Each GitHub release publishes `SHA256SUMS` and, for every artifact, a sigstore bundle `<artifact>.sigstore.json` (`cosign sign-blob --bundle`), which includes the transparency-log inclusion proof needed to verify after the short-lived signing certificate has expired:

   ```sh
   cosign verify-blob --offline --trusted-root trusted_root.json \
     --bundle ogentic-audit-<target>.sigstore.json \
     --certificate-identity "https://github.com/OgenticAI/ogentic-audit/.github/workflows/release-cli.yml@refs/tags/v<version>" \
     --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
     ogentic-audit-<target>
   ```

   The expected identity, `trusted_root.json` (the sigstore public-good root), and `SHA256SUMS` are obtained **independently** of the bundle, through the same channel as the pin or from the public release page. Copies inside a bundle are a convenience only.
3. **A verifier inside a bundle** is attested (§11.1), so the stock check of §11.7 verifies its bytes against the signer's key before it is run. That ties it to the signer; step 2 ties it to the public build. Instructions put the stock check first.

### 11.9 Instructions file

`HOW-TO-VERIFY.txt` is an attested file (role `instructions`). The builder writes this text, filling in only the release id and the minimum version:

```text
How to check this release

This folder was signed when it was released. You can check that nothing in it has been
changed, without trusting whoever gave it to you and without any secret.

1. Get the signer's key fingerprint FROM THE SIGNER, not from this folder: from their
   website, a letter, a filing, or by phone. It is 64 characters long, usually written
   in 16 groups of 4. Any fingerprint printed inside this folder could have been replaced.

2. Check the signature and every file with standard tools, as described at
   https://github.com/OgenticAI/ogentic-audit/blob/main/docs/guides/verifying-a-release.md
   This needs only OpenSSH and Python, which most computers already have.

3. To also check the audit log, use ogentic-audit version 0.4.0 or later. Download it
   from https://github.com/OgenticAI/ogentic-audit/releases and check it as that page
   explains. Do not run a verifier from this folder until step 2 has passed. Then run:

     ogentic-audit verify-release . --key-fingerprint "<the fingerprint from step 1>"

   "Verified" means every file and the audit log are exactly as signed. "Not verified:
   you did not supply the signer's key" means you skipped step 1. Anything else names
   what changed, what is missing, or what was added.

Release: <release_id>
```

It MUST NOT print the signer's fingerprint as the one to use. The plain-language guide it links to ([`docs/guides/verifying-a-release.md`](../guides/verifying-a-release.md)) covers macOS, Linux, and Windows, what each result and exit code means, and what verification does not prove.

## 12. Downgrade and confusion rules (summary)

1. A signed-mode verification of an HMAC (`0x0001`) log is never `Verified`: the error `HmacLog` for a whole log under a pin, `FormatDowngrade` for a segment inside a signed log or for a log inside a release.
2. HMAC verification needs a key given explicitly. No implicit key source is ever used, and an HMAC `Verified` is labelled shared-key.
3. An HMAC-mode verification of a signed log is an argument error, never a silent pass.
4. A log never mixes formats, algorithms, `log_id`s, or keys (H3, H10).
5. `sig_alg` is inside every signed envelope and every hashed header. The key type is inside `key_id` and every SSHSIG. Every JSON `alg` names its signer's key type. The verifier checks they agree and never infers an algorithm.
6. Namespaces separate records, checkpoints, witness co-signatures, attestations, transitions, acceptances, and revocations, and scopes limit each key to its namespaces.
7. Only `sha512` SSHSIGs, strict Ed25519 (§3.5), no weak keys.
8. v1 and v2 checkpoints are not interchangeable.

## 13. Library and CLI surface

This section is normative for the shapes a consumer depends on. It names the API as implemented for 0.4.0.

### 13.1 Rust: `ogentic-audit-core`

- **Keys:** `SigAlg`; `PublicKey` (`parse` from any §3.7 form, `to_openssh(comment)`, `to_pem()`, `to_hex()`, `fingerprint()`); `Fingerprint` (`parse`, exactly 32 bytes; `to_grouped_hex()`, `to_dashed_hex()`, `to_openssh()`; equality only, never prefix comparison).
- **Signing:** `trait Signer: Send + Sync { fn public_key(&self) -> &PublicKey; fn sign(&self, namespace: &str, message: &[u8]) -> Result<Signature, SignError>; }`. `SignError` is `#[non_exhaustive]`, with `Unavailable`, `Cancelled` (a user prompt was dismissed), `FaultDetected` (the signature failed its own check, §7.1), and `Backend(String)`. Signing can fail for any key that is not in process memory: a hardware or OS-protected key, KMS, PKCS#11. `InMemorySigner::from_seed([u8; 32])` and `generate()`, zeroized on drop, derive the public key from the seed and never accept one from the caller.
- **Writing:** `log_format(dir) -> io::Result<Option<u16>>` (`None`: no segments), so an embedding application can keep appending to old HMAC logs and open new signed ones. `SignedWriter::open_signed(dir, Box<dyn Signer>, session_id) -> Result<SignedWriter, WriterError>` (a separate type from the HMAC `Writer`, which is unchanged), with `WriterError::FormatMismatch { found: u16 }`, `WriterError::Sealed`, and `WriterError::Sign(SignError)`. `SignedWriter::last_record_hash()`, `SignedWriter::log_id()`, `SignedWriter::seal()`.
- **Trust and verification:** `TrustContext` (`pin(key_or_fingerprint, principal, scope)`, `pin_key`, `pin_fingerprint`, `from_allowed_signers`, `add_statements(dir, operator)`, `add_revocation(file)`), `SignedVerifier::new(TrustContext).verify_with_options(dir, SignedVerifyOptions)` returning a `SignedVerifyReport` (format version 2) or a `SignedVerifyError` (§8.4, with `exit_code()`).
- **Checkpoints and statements:** `checkpoint::{CheckpointV2 (to_bytes, parse, sign), cosign, compare}`; a checkpoint and its witness co-signatures are checked against a log by passing them to the verifier (`SuppliedCheckpoint`). `statements::{transition(old: &dyn Signer, new: &dyn Signer, final_heads, final_releases, issued_at, reason), accept, revocation(revoker: &dyn Signer, revoked, cut_points, issued_at, reason), krl(revoked_keys, …)}`.
- **Releases:** `release::AttestationBuilder` (§11.3: `add_file(FileSpec { path, role, parts })`, `add_log(LogSpec { source, path, head, elide })`, `add_statement`, `add_witness`, `write(&dyn Signer) -> Result<AttestationDigest, ReleaseError>`), and `release::verify_release(dir, &TrustContext, &ReleaseOptions) -> Result<ReleaseReport, ReleaseError>`. `ReleaseReport` is separate from the log report, because a log location cannot name a release item: its violations carry `enum ReleaseItem { Attestation, File { path, part: Option<String> }, Log { path, segment, record }, Key { key_id } }`.
- **Records:** `reader::Record` is unchanged (format `0x0001`). Signed records are read, without verification, with `signed::visit_records(dir, f)`, which yields a `RecordView` (envelope, body or none when elided, `record_hash`, signature).
- **`FORMAT_VERSION`** stays `0x0001`; `FORMAT_VERSION_SIGNED = 0x0002` is added.
- **Semver.** 0.4.0 marks every public type that will grow `#[non_exhaustive]`: `ViolationKind`, `Verdict`, `ViolationEvidence`, `HeaderCorruptSubkind`, `RecordCorruptSubkind`, `HeaderParseError`, `RecoveryAction` (variants), and `VerifyReport`, `LogSummary`, `Violation`, `VerifyOptions` (with a `Default` and builder, since the CLI builds it with a struct literal today), `RecoveryReport` (fields). The CHANGELOG tells consumers that a wildcard arm over `Verdict` or `ViolationKind` MUST fail closed: an unknown verdict is not a verification.

### 13.2 Rust: `ogentic-audit-keychain`

`KeychainSigner::{create, load, load_or_generate, delete}(service, account)`. Use an account distinct from any HMAC key, for example `<app>:ed25519`.

- **Item value:** the tag `ed25519-seed:v1:`, then the 32-byte seed, then the 32-byte public key. The HMAC loader requires exactly 32 bytes, so neither key can be loaded as the other. On load, the signer derives the public key from the seed and compares it with the stored copy; a mismatch (wrong item, corruption) is an error, never a silent new key.
- **Create-only.** `create` and `load_or_generate` hold an exclusive lock file in the user's configuration directory while they check that the item is absent, write it, and read it back. Two processes can then never overwrite a seed whose fingerprint may already be published.
- **Public key without a prompt.** The public key is also written as a non-secret file (`<account>.pub` in the configuration directory), so `key fingerprint` does not unlock the keychain. It is for display only; signing always derives the key from the seed.
- **What each platform's store guarantees** (none is a hardware key; the `Signer` trait allows one later):

| Platform | Store used | Guarantee | Not guaranteed |
|----------|-----------|-----------|----------------|
| macOS | login keychain (file-based) | encrypted at rest under the user's login; not synced to iCloud Keychain | it moves to a new Mac with Migration Assistant or a Time Machine restore. A device-only item needs the data-protection keychain, which requires an app signed with a provisioning profile; a CLI cannot have one. An application that can MAY implement `Signer` over a `…ThisDeviceOnly` item |
| Windows | Credential Manager, with persistence **local** (`Entry::new_with_modifiers(service, account, {"persistence": "local"})`) | stays on this machine for this user | the default (`enterprise`) roams with the user profile, so it MUST NOT be used |
| Linux | Secret Service | encrypted under the user's login keyring | no notion of a device; absent on headless machines, where the signer is unavailable. `keyutils` loses its contents at reboot and is never used for seeds |

- **Never** exported in OpenSSH private-key format, and never loaded into `ssh-agent` (§7.1). `key export` exports public keys only.

### 13.3 Python: `ogentic_audit`

- `SigningKey.generate() / from_seed() / from_keychain(service, account)`, `.public_key_openssh(comment)`, `.fingerprint()` (grouped hex), `.fingerprint_openssh()`. Tests use `SigningKey.from_seed(bytes.fromhex(os.environ[...]))`, the counterpart of an HMAC test key in an environment variable.
- `Writer.open(dir, signing_key=…)`.
- `verify(log_dir, key=None, *, public_key=None, key_fingerprint=None, trust=None, statements=None, revocations=None, checkpoint=None, expect_log_id=None, raise_on_violation=False)`. `key` (an HMAC `KeyHandle`) becomes optional and keeps its position, so existing calls work; every new argument is keyword-only. `checkpoint(log_dir, key=None, *, signing_key=None)` likewise.
- The report (`SignedVerifyReport`) has `.verdict` (`"Verified" | "SelfConsistent" | "Violation"`), the existing `.verdict_kind`, `.ok` (true **only** for `Verified`), `.reason`, `.final_record_hash_hex`, `.log_id_hex`, `.head_anchored`, `.elided_records` (`"s0r1"` positions), `.signer` (a dict as in §14), `.violation`, `.additional_violations`, `.warnings`, `.to_json()`, and `.render(ascii, program)` (the human report). For a signed log, `checkpoint=` takes v2 checkpoint files (their `.sig` beside them).
- Exceptions: `SignerNotPinnedError(OgenticAuditError)`, **outside** the tamper hierarchy, raised by `raise_on_violation=True` for `SelfConsistent`. One subclass of `VerificationFailed` per new violation kind. An unknown kind raises `VerificationFailed` itself, so it fails closed.
- `attest_release(release_dir, *, files: Sequence[str | FileSpec], logs: Sequence[LogSpec], signing_key, release_id) -> str` returns the attestation's SHA-256 (for `final_releases` and `trusted_releases`). `FileSpec(path, role=None, parts=())`, `LogSpec(path, head=None, elide=())`.
- `verify_release(release_dir, *, public_key=None, key_fingerprint=None, trust=None, statements=None, revocations=None, witnesses=None, expect_release_id=None, allow_unattested=False) -> ReleaseReport`, with `.verdict`, `.ok`, `.violations` (dicts with `item`, `kind`, `reason`, `evidence`), `.warnings`, `.files`, `.logs`, `.to_json()`.
- `python -m ogentic_audit verify-release …` and `python -m ogentic_audit verify …` print the same output and exit with the same codes as the Rust CLI, so the Python package is usable by someone who does not program. (The one difference is the re-run hint after "Not verified", which names `python -m ogentic_audit` so that the reader can run it.)

### 13.4 CLI: `ogentic-audit`

- `verify` reads the format first and loads an HMAC key only for format `0x0001` and only when one was given on the command line (§8.1). The current default `--key-source env` therefore no longer applies implicitly to `verify`, `checkpoint`, or `export`. That is a breaking change in 0.4.0, noted in the CHANGELOG; `--key-source env` given explicitly still works.
- New flags: `--public-key`, `--key-fingerprint`, `--trust`, `--statements`, `--revocations`, `--witness`, `--expect-log-id`.
- **`--segment N`** narrows the report; it never improves the verdict. It runs in forensic mode, so segments after a failing one are still checked. It removes only violations located in other segments, and keeps every log-level kind whatever the segment: `UntrustedSigner`, `FormatDowngrade`, `UnsupportedAlgorithm`, `RevokedKey`, `RetiredKey`, `LogIdMismatch`, `TransitionEquivocation`, `CheckpointForDifferentLog`. For a signed log the verdict stays the whole log's: a log with a violation elsewhere still fails (the report says how many violations it left out), and an unpinned log stays `SelfConsistent`. For format `0x0001` the forensic run fixes the old behaviour, where a run that stopped at a violation in segment 0 reported `--segment 1` as `Verified` without having read segment 1.
- New subcommands: `verify-release`; `checkpoint [--sign]`, `checkpoint compare`; `witness`; `key generate | export [--format openssh|pem|hex] | fingerprint | transition | accept | revoke | krl` (with `keygen` and `export-public-key` as top-level aliases). A signing key is named `keychain:<service>:<account>`, `file:<path>` (a 0600 file holding the hex seed, for tests and CI) or `env:<VAR>`. `show` and `head` read both formats.
- **`export`** (the court PDF) states what was checked for the log's format: for `0x0001`, an HMAC check with a shared key; for `0x0002`, the signer's fingerprint and principal, the trust path, whether the head is anchored, and the count of elided records. It needs no key for a signed log. The current HMAC-only wording is not used for signed logs.
- **Exit codes:** 0 verified; 1 violation; 2 I/O; 3 argument; 4 not verified because no key was supplied or nothing was signed; 64 usage. The CLI parses with `try_parse` and maps parser usage errors to 64, as already documented (the parser's own default is 2, which collides with I/O); help and version exit 0. The `--help` table lists all six.
- Human output follows §11.6 for `verify` as well: the whole report on standard output, every violation listed and grouped, full fingerprints, ASCII fallback.

## 14. Report format, `format_version` 2

[`violation-report.md`](violation-report.md) applies, with these changes for v0.2 logs. The document and a JSON Schema for it are updated in the implementing change.

- `format_version: 2`; `verdict` adds `"SelfConsistent"`.
- `log.final_hmac_hex` is replaced by `log.final_record_hash_hex`. Added: `log.log_id_hex` (32 hex digits), `log.head_anchored`, `log.sealed`, `log.elided_records` (count and positions), `log.unsigned_last_segment`.
- A `signer` block: `{ "principal", "alg", "key_id_hex", "fingerprint_grouped", "fingerprint_openssh", "trusted": bool, "trust_path": [key_id_hex…], "reason": "pinned" | "transition" | "not_pinned" | "no_signed_records" }`.

- A `warnings` array: `UnsignedLastSegment`, `RolledOverWithoutSuccessor`, `NearMissSegmentName`, `TornTailAfterHead`, ignored statements.
- New kinds:
  - `SignatureInvalid` (`reason`: `missing`, `malformed`, `namespace`, `hash_alg`, `key_type`, `reencoded`, `weak_key`, `body_mismatch`, `mismatch`);
  - `UntrustedSigner` (`reason`: `not_trusted`, `out_of_scope`; `expected`: pinned fingerprints and principals; `actual`: signer fingerprint);
  - `RevokedKey`, `RetiredKey`, `TransitionEquivocation`, `AlgorithmMismatch`, `UnsupportedAlgorithm`, `LogIdMismatch`, `SealedLogExtended`, `CheckpointForDifferentLog`, `FormatDowngrade` (`expected_version`, `actual_version`);
  - `RecordCorrupt` subkinds `TooLarge`, `BadRollover`, `ElidedStructural`;
  - for releases: `AttestationMissing`, `AttestationMalformed`, `ReleaseIdMismatch`, `FileMissing`, `FileAltered` (`reason`: `size`, `part`, `outside_parts`, `content`, `not_regular_file`, `ambiguous_name`; `expected_sha256`, `actual_sha256`, `expected_size`, `actual_size`, `part` {`name`, `offset`, `length`} or null), `UnattestedFile`.
- `HmacMismatch` does not occur for v0.2 logs.
- v1 reports (format `0x0001`) are unchanged except for one added member, `"authentication": "shared-key"` (§8.1).

`ts_wall`, `head_ts_wall`, `observed_at`, and `created_at` are each the clock of whoever signed them. A report never presents them as independently established time. Trusted time (an RFC 3161 token over a checkpoint or attestation) is a later, additive artefact.

## 15. Post-quantum

`sig_alg 0x0002` is reserved for ML-DSA-65 (FIPS 204) and is **not implemented**. When it is, the header gets `P` = 1952, signatures are 3309 bytes, a key type string for fingerprints is fixed, and golden vectors are added. The byte layouts are parameterized by `sig_alg`, so the log format needs nothing else. Three things do change:

- **The stock-tools path does not carry over.** OpenSSH has no ML-DSA key type for SSHSIG today, so `ssh-keygen` cannot check an ML-DSA attestation. Until it can, the post-quantum path has only the `ogentic-audit` verifiers and independent implementations of this spec.
- **A transition is only as strong as the key that signed it.** An ML-DSA key reached through an Ed25519-signed transition is trusted only as long as Ed25519 holds. For the long-term claim, pin post-quantum keys directly, or rely on a transition only together with a trusted timestamp showing it existed before Ed25519 could be forged. Transitions never go to a weaker algorithm (§9.3).
- **Checkpoints and attestations made today are Ed25519-signed.** Evidence made now is defended in the long term by checkpoints and attestations held by others and **timestamped** by a trusted time-stamping authority before Ed25519 could be forged. Any checkpoint relied on for that claim needs such a timestamp. A log or attestation created after that point proves nothing by its Ed25519 signature alone.

**Generated at test time, not committed.** Git cannot reliably carry some cases: macOS (`core.precomposeunicode`) rewrites NFD names, Windows checkouts turn symlinks into text files, and APFS cannot hold two names that differ only in case or normalization. The test suite generates `release-nfd-name` (expected `Verified`), `release-symlink` and `release-reparse-point` (`FileAltered`, `not_regular_file`), and `release-ambiguous-name` (`FileAltered`, `ambiguous_name`; Linux only).

**Independent oracle.** `tools/gen_vectors.py` generates the vectors with Python `cryptography` (OpenSSL's Ed25519), an implementation independent of the Rust core's `ed25519-dalek`, so byte agreement is a genuine cross-implementation check. Its `--verify` mode is a second verifier, used as a test oracle for every expected result above. It applies §3.5 rules 1–3 itself, against Appendix A and by the torsion check, because OpenSSL does not. The PyO3 bindings wrap Rust and do not count as independent. Detached signatures in the vectors MUST also verify with `ssh-keygen -Y verify` where the vector expects success, and CI runs that check where OpenSSH is available, including the documented differences of §3.5 (`reencoded`, and a weak-key signature that `ssh-keygen` accepts).

## 17. Versioning and compatibility

- Format `0x0001` is frozen. It keeps working in every API, the CLI, and the Python package, with its report shape (`format_version: 1`, plus the additive `authentication` member). Two CLI behaviours change in 0.4.0, both in the direction of failing closed: an HMAC key is no longer taken implicitly from the environment (§13.4), and `--segment` no longer reports `Verified` for a segment it did not check.
- Format `0x0002` is a separate mode selected by the writer at log creation. There is no in-place conversion. Re-signing an HMAC log would make the new key vouch for history it never witnessed.
- 0.3.x verifiers misreport v0.2 logs as tampered (§4). Instructions and the guide say "requires ogentic-audit 0.4.0 or later".
- Library versions: the implementing release is **0.4.0** for every **published** crate (`ogentic-audit-core`, `ogentic-audit-keychain`, `ogentic-audit`) and the Python package, because public enums and structs gain variants and fields and become `#[non_exhaustive]` (§13.1). `ogentic-audit-kms` is unpublished (`0.2.0-pre`) and outside the release workflow; a KMS-backed `Signer` follows separately. The crate and PyPI descriptions, which say "HMAC-SHA256 chained", are updated to name both modes. The CHANGELOG carries a 0.4.0 migration note.
- Reserved: `sig_alg` values (§3.2), envelope keys ≥ 100, header `reserved`, and the `attestation` record field named in ADR-0001 (still unassigned; witnesses use co-signatures, §10.2).
